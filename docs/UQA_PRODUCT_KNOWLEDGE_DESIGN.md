# UQA: проектирование масштабируемых знаний о продукте

Статус: предложение архитектуры для обсуждения до реализации. Дата: 14 октября 2026. Это не подтверждённый факт о продукте, не релиз новой подсистемы и не инструкция изменения стенда. Документ не импортируется в продуктовый индекс автоматически. Дополняет UQA_KNOWLEDGE_FOUNDATION.md.

## 1. Цель и главное разделение

Память должна объяснять устройство и поведение продукта, а не пересказывать все действия тестировщика. Общие знания доступны QA, документации, разработке и техподдержке с разными правами. История каждого полезного теста сохраняется, но далеко не каждый прогон создаёт новое продуктовое знание.

Предлагаются три логических слоя. Это не требование немедленно установить три разных БД.

| Слой | Что хранит | Что получает LLM |
|---|---|---|
| Источники и история | Документы, исходный код разрешённых репозиториев, Jobs, evidence, observations, trace и исходы | Только отобранные и разрешённые фрагменты при необходимости |
| Канонические знания | Компактные утверждения, контракты, рецепты, ограничения и связи с источниками | Основной ответ с областью применимости и ссылками |
| Поисковые проекции | FTS, позднее embeddings и индексы связей/символов | Кандидатов для получения актуальных записей, не самостоятельную истину |

Первичные источники могут расти с количеством прогонов. Активное продуктовое ядро должно расти главным образом с новыми функциями, вариантами поведения и версиями, а не с количеством повторных кликов. Индексы являются восстановимыми проекциями, а не единственным местом хранения знаний.

Сейчас существуют FTS5 по документам и отдельный product_knowledge_store с facts, confirmations, fact_scopes и историей статусов. Нынешний безопасный retrieval поддерживает только ui_navigation/ui_api_binding. Эволюция должна использовать эти границы и миграции, а не заменить их произвольным текстом с ярлыком verified. Новые типы подключаются по одному с собственным validator.

## 2. Единица знания: не абзац отчёта, а утверждение

Основная запись описывает одну проверяемую мысль. Примеры:

- Контракт: какой вход принимает функция, какова семантика результата, какой источник задаёт expected.
- Наблюдаемое поведение: на определённой версии операция даёт определённый результат при явно указанных условиях.
- Рецепт: последовательность допустимых шагов с prerequisites, проверками и обработкой неопределённости.
- Ограничение: наблюдённое несовпадение поведения и ожидания, обходной путь отдельно от доказанной причины.
- Code binding: связь API/функции продукта с символом кода и точным commit.
- Тестовый сценарий: переиспользуемый oracle и prerequisites; результаты прогонов остаются отдельными событиями.

Fixture UQA проверяет механизм UQA. Он не становится знанием о поведении U-Connect. Product namespaces разделяют эти области. Проектные решения/roadmap также отдельны от продуктовых фактов.

Одна функция имеет устойчивый concept ID, описание, aliases и варианты по версиям. UI-имя, API path и имя Python-функции — её bindings, а не три дублированных объяснения. Семантическую идентичность нельзя назначать только свободной формулировкой модели; aliases и соответствия проходят проверку.

## 3. Общий контракт записи

Обязательные общие поля: schema_version, record_id, revision_id, product_namespace, concept_id, knowledge_kind, утверждение/структурированное содержание, применимость, происхождение, уровень проверки, даты, права доступа и связи. Специальные поля зависят от типа, без мешка произвольных необязательных JSON.

Применимость включает только существенные измерения: feature/profile, backend/frontend/agent/plugin версии, ОС/архитектура, настройки или deployment scope. Не нужно размножать общий факт по всем комбинациям параметров. Неизвестная identity остаётся unknown. Отдельно хранить tested_on и declared_compatible: проверка двух версий не доказывает промежуточный диапазон.

Уровни источников не смешиваются:

- declared_spec: ожидаемое поведение из заданного пользователем критерия/утверждённой спецификации;
- static_implementation: что видно в исходном коде конкретного commit;
- runtime_observation: что действительно наблюдалось в выполнении;
- hypothesis: предположение, которое надо проверить.

Статус candidate/verified/conflict/deprecated относится к конкретному утверждению и scope. Execution mode live_operator_assisted/live_autonomous/isolated_fixture независим от статуса. Проверенный результат одного теста не повышает автоматически все предложенные моделью объяснения до verified.

Происхождение: точные document revision/commit, Job/case/evidence/observation IDs, тип проверки, исполнитель, дата, границы вывода. У источника и самого извлечения есть hash/version. Дата наблюдаемого события и дата его обработки различаются. Для воспроизводимой исторической проверки желательны observed_at и recorded_at.

Связи: supported_by, contradicts, supersedes, depends_on, implements, tested_by. Важно отличать конкретную ссылку от утверждения о доказанной причинности. Причина дефекта, извлечённая моделью из симптома, остаётся hypothesis.

## 4. Дедупликация и сдерживание роста

Разные механизмы решают разные задачи:

1. Event ID и outcome revision устраняют повторную обработку одного результата, но сохраняют исправленные итоговые события.
2. Content hash очищенного источника/нормализованного payload исключает точные копии. Не индексировать секреты и их производные без отдельной безопасной политики.
3. Canonical key из namespace, concept, predicate и нормализованных условий объединяет повторные подтверждения. Сам текст, локальный test-resource name и случайный GUID не являются semantic key.
4. Совпадение формулировок/embeddings предлагает near-duplicate для проверки, но не сливает автоматически разные условия или противоположные утверждения.

Повтор того же поведения обновляет confirmation summary: first/last seen, количество уникальных поддерживающих событий, границы tested_on. Число повторов одного run не считается независимым подтверждением. В основной выдаче ограниченный набор репрезентативных evidence; полная история доступна отдельно и не добавляется в каждый prompt. Изменившееся поведение создаёт вариант/конфликт, а не молча заменяет прежний факт.

Условия рецепта All хранятся один раз; четыре текущих machine IDs и количество машин относятся к конкретному snapshot. Повтор создание новой uqa-test-коллекции не создаёт новую версию общего рецепта, если механизм не изменился.

Индексируется не вся история. В активном поиске — актуальные записи, релевантные ограничения и необходимые исторические варианты. Документы делятся по разделам, код — по символам; не по произвольным одинаковым кускам вне структуры. Общие описания не копируются в каждом chunk; scope/provenance передаются отдельно при выдаче.

Обновление источника перерабатывает только изменившиеся разделы/символы; embeddings, если будут нужны, пересчитываются по комбинации content hash + модель/параметры embedding. Производный индекс можно перестроить без повторного запуска бизнес-тестов.

## 5. Размер, хранение и отсутствие скрытого удаления

Измерять отдельно размер первичных evidence, числа/объём канонических записей, историю confirmations, FTS/vector индекс, backlog и bytes added per run. Сравнивать число новых концептов с числом новых записей; аномальный рост служит сигналом дублирования или плохого extraction, не поводом удалить историю.

Предварительные ограничения: лимит candidate records на событие, лимит длины каждого типа, ограниченный retrieval context, бюджеты источников/проектов и throttling ingestion. Конкретные значения выбираются после измерений; не подменять их обещанием «база не растёт».

Hot/cold архивирование и retention — отдельное согласуемое правило. Действующее решение пользователя сохранять Jobs и секреты остаётся в силе: проектирование памяти не разрешает их очистку. До согласования при нехватке места ingestion приостанавливается с диагностикой, а не silently удаляет данные или понижает защитный порог. Краткое summary не заменяет доказательство без разрешённой политики хранения.

## 6. Как обновления продукта меняют знания

Идентичность знания, его revision и release binding раздельны. Одна общая семантика может иметь подтверждения нескольких релизов без полной копии текста на каждый релиз. Нельзя автоматически переносить verified на следующий patch/minor или объявлять совместимость по похожему UI.

Change detection по Git diff/API schema/UI binding отмечает связанные знания needs_recheck, но само изменение строки не доказывает изменение бизнес-семантики. Через depends_on формируется приоритетная очередь перепроверки затронутых функций/контрактов. Инвалидация verification не означает «старый факт был ложью».

Противоречие спецификации и runtime не разрешается рейтингом источников: хранить expected и actual отдельно, создавать limitation/conflict. Для code ↔ runtime аналогично: статическая ветка кода не доказывает её выполнение и не даёт причину ошибки без проверки пути.

## 7. Будущая память о коде

Подключать только явно разрешённые репозитории, с правами отдельно от доступа к лабораторному стенду. Не выгружать приватный код во внешние модели/embedding service без разрешения.

Код индексировать структурно: repository identity, commit, file path, symbol ID, сигнатура, тип, definition/reference/implementation links и диапазон исходного текста. Комментарий, docstring и краткое LLM объяснение — подсказки; утверждение о реализации подкрепляется ссылкой на код. Оригинальный код читается по точному snapshot, не переписывается целиком в каждую knowledge card.

Предлагаемая цепочка: функция продукта → UI/API contract → endpoint/handler → символы реализации → тест/оракул → runtime evidence. Например, Manual refresh коллекции связывается с проверкой launch_type и отправкой команды, а пустой RAM столбец — с renderer и типом child detail, без выдуманного root cause.

SCIP — возможный переносимый формат definition/reference/implementation индекса для разных языков; выбор конкретного indexer требует проверки языка/репозитория. Dynamic calls, конфигурационные связи, reflection и реальные причинные зависимости могут потребовать runtime traces: статический индекс не даёт полного call graph. [SCIP Code Intelligence Protocol](https://github.com/scip-code/scip).

При изменении commit ссылки на строки не переносить вслепую. Для symbol/content-неизменных участков допускается проверяемое reuse binding; semantic rename требует явного mapping. Прежний snapshot остаётся пригодным для разбора старого релиза.

## 8. Retrieval для разных агентов

До поиска применяются права и изоляция проекта/организации; заголовки/пути приватного источника тоже не должны утекать. Версия, kind и scope ограничивают кандидатов, а не исправляют неподходящий ответ постфактум. При загрузке canonical record повторно проверять текущие ACL/status/revision: устаревший индекс не должен обходить отозванные права или возвращать deprecated как текущую истину.

FTS подходит для точных терминов, endpoint и символов. Semantic search полезен для пользовательских перефразирований; добавлять его только после оценки текущих пропусков. Graph/relationship traversal помогает связать симптом с функцией и кодом. Это комбинируемые проекции одних знаний, не три копии пользовательского опыта.

Результат должен содержать запись и revision, применимость, тип источника, verification status, ограничения и ссылки. Слишком большой/усечённый результат явно помечается и не принимается как полный контракт. Unknown scope и отсутствие подходящего знания ведут к уточнению/текущей диагностике, не к угадыванию последнего релиза.

QA нужен рецепт/expected/observed; документации — declared contract с предупреждениями о расхождениях; разработке — точный код, связи и regression cases; техподдержке — симптомы, диагностика и подтверждённые обходы. Это представления одной базы, не независимые переписываемые энциклопедии. Доступ к памяти никогда не выдаёт stand WRITE. Инструкции из документов/кода остаются недоверенными данными.

## 9. Safe ingestion и продвижение знаний

Pipeline: итоговое событие → durable outbox → извлечение candidates → очистка/ACL/schema/scope validation → dedup/conflict check → проверка допустимых источников → canonical revision/confirmation → поисковые проекции.

Worker предполагает at-least-once delivery и idempotent sink. Нельзя обещать exactly-once общей транзакцией через две нынешние SQLite БД. Запись consumed и подтверждение sink должны иметь crash-recovery протокол. Потеря knowledge worker не запускает повтор теста или действия на стенде.

Candidate extraction может помогать LLM, но LLM не повышает свой вывод до verified. Правила promotion зависят от knowledge kind и уровня доказательства. Нет универсального «три PASS — значит всё верно»: неправильный oracle может повторяться. Наблюдённый факт, нормативный контракт и recipe acceptance имеют разные проверки.

Непроверенный/сомнительный источник quarantine; секретные исходники не индексируются целиком. Документ/код/trace не может сам назначить себе доверенный status или разрешение. Версия extractor/validator сохраняется для воспроизводимости.

Согласованность canonical и index контролируется generation/revision и проверкой integrity; незавершённая публикация не выдаётся как принятая knowledge revision. Read API и экспортные пакеты получают версионируемую схему и проверяемый manifest, а не прямую копию приватной БД.

## 10. Приёмка до автоматического пополнения

Минимальные обязательные сценарии будущих тестов:

- 10000 повторных событий неизменного поведения не создают 10000 продуктовых cards; exact duplicate event не увеличивает independent confirmation count.
- Outcome correction сохраняет историю и корректно отзывает прежнее основание, если оно больше недействительно.
- Близкие тексты с разными условиями не сливаются; противоположный actual создаёт conflict.
- Wrong/unknown version не возвращает verified знание чужого релиза; declared compatibility не становится tested_on.
- Fixture не становится продуктовым фактом; операторский прогон не считается автономным; speculative diagnosis не становится root cause.
- Секреты, запрещённые source paths и prompt injection не проходят в общий retrieval; отозванный ACL действует даже при старом индексе.
- Crash между canonical write/index update/event ack не теряет событие и не дублирует действие на стенде.
- Изменение одной функции переиндексирует только затронутые единицы; полный reindex восстановим из разрешённых canonical sources.
- Кодовая ссылка открывает правильный commit/symbol; rename/dynamic call не дают выдуманной связи.
- Retrieval сравнивается на фиксированном корпусе реальных задач, перефразирований, неизвестных функций и обновлений: relevance, version accuracy, citation validity, abstention, token cost и latency. Рост recall не допускается ценой утечки/ложного PASS.

10000 — предложенный нагрузочный fixture для дедупликации, не выполненный тест и не обещание производительности. Порог задержки/объёма будет принят после baseline измерений. Внешняя graph/vector БД не вводится до доказанного ограничения существующего storage.

## 11. Порядок реализации после обсуждения

1. Принять taxonomy/identity/scope/provenance и состав обязательных полей; сопоставить с existing facts/scopes без изменения verified history.
2. Внедрить typed validators и миграции на временной копии с backup/restore и negative tests.
3. Сделать idempotent ingestion/dedup/conflict и bounded confirmation summaries; прежде всего корректность, затем индексацию.
4. Подключить safe outbox exporter итогов всех нужных типов; fixtures и продуктовые события изолировать namespace/mode.
5. Реализовать read retrieval contract с ACL/version/revision gates, reuse FTS и measured context budget.
6. После получения доступа подключить один кодовый репозиторий/язык, символы и цепочку одного реального feature-to-code-to-test примера.
7. Добавить semantic retrieval/общий агентский API/архивирование по результатам оценки и согласованным правам, не заранее ради масштаба.

## 12. Источники архитектурных ориентиров

W3C PROV задаёт ориентир для происхождения и производных записей, а не готовый inference engine. [PROV overview](https://www.w3.org/TR/prov-overview/).
FTS5 может отделять поисковые данные от external content, но согласованность требует явного механизма обновления и проверок; переход текущего индекса на этот режим пока не сделан. [SQLite FTS5 external content](https://www.sqlite.org/fts5.html#external_content_tables).
SCIP описывает language-agnostic code indexing для навигационных связей; интеграция и способность LLM рассуждать о коде требуют собственных проверок. [SCIP](https://github.com/scip-code/scip).
