# UQA — техническая доработка до пилота

Решение пользователя, 14 октября 2026: прежняя цепочка из 12 этапов больше не является текущим планом работ. Jira и пилот с отделом отложены; VPN недоступен. Исторические результаты сохраняются, но отсутствие обратной связи отдела не блокирует техническую разработку.

## Порядок и условия готовности

| № | Технический шаг | Что должно быть доказано | Текущий статус |
|---|---|---|---|
| 1 | Идентичность тестового ресурса | Нельзя заменить известный ledger ID; первое заполнение ID не допускает чужой объект, произвольный текст или ошибочный ответ | v165: guard resource_update, профильный smoke и runner 205/205 PASS. Первичная resource_register, legacy записи и полная связь с create-операцией требуют отдельного аудита |
| 2 | Durable журнал изменяющих операций | Намерение записывается до отправки commit; после сбоя оно не теряется. Ключ операции связан с конкретным workflow/stage/resource, а не только с одинаковой кнопкой Save | v167: отдельный authoritative журнал, POSIX claim lock, pre-send запись и replay barrier в штатном Core. Runner 207/207 PASS. Поддержаны известные commits и explicit locked stages; autosave/legacy без Job не покрыты. Общие RMW-гонки Job остаются отдельно |
| 3 | Разрешение неопределённого результата | Потерянный ответ/таймаут ведёт к чтению текущего состояния, а не слепому повтору. Отсутствие доказательства не даёт разрешения повторить изменение | v168: evidence-only reconciliation; свежий полный GET, baseline, case/session/origin и неизменный oracle. Runner 208/208 PASS. Старый/частичный ответ не снимает барьер, resend не разрешается. Это подтверждение состояния, не причинности и не бизнес-PASS |
| 4 | Автономный lifecycle-контракт | Один сценарий create → read → name-only edit → read → cleanup. Проверки вычисляются по пригодным evidence одного ресурса и одинаковому серверному ID; модель не назначает успех сама | v169: immutable runtime-протокол трёх стадий, proof-gated advance, typed ID binding и отдельный ledger binding. Профильный offline smoke PASS. Полная автономная бизнес-приёмка ещё не реализована: declared owned workflow не получает PASS от модели |
| 5 | Область изменений и cleanup | Разрешения ограничены owned ресурсом и allowlist полей/значений. Проверяются известный ID, пустота/зависимости и точный адрес; альтернативный UI cleanup не обходит эти ограничения | v164 REST ID guard реализован. UI-путь, legacy ID и повторное выполнение требуют доработки |
| 6 | Планировщик связанных операций | Один workflow не превращается в независимые создания объектов; проверки не теряются, стадии зависят друг от друга и используют одну запись ресурса | v169: explicit locked blueprint ведёт один case через три стадии одного ID; одинаковые Save различаются stage ID. Natural-language compiler такого blueprint и широкий planner остаются |
| 7 | Универсальные формы и многошаговые интерфейсы | Поля, validation, динамическая доступность, выборы, диалоги и мастера проверяются по наблюдённым признакам; неопознанное не угадывается. Нет привязки к координатам/UC-specific ветвлениям Core | Есть большая библиотека инструментов и ограниченные live proofs; не покрывает произвольный frontend |
| 8 | Память о версиях и функциях | Знание помогает найти функцию, но перепроверяется на текущем UI/API; старый binding не становится evidence для PASS | Navigation memory проверена; широкий UI/API binding и смена версии остаются |
| 9 | Диагностика и журнал блокеров | Различаются ошибка агента, дефект продукта, инфраструктура и неподдержанный критерий. Причина и условия перепроверки сохраняются на диске, не только в контексте модели | Основа реализована; нужен сквозной аудит и уточнение классификации |
| 10 | Техническая приёмка релизного набора | Общий runner, изолированные сбои/повторы/конкуренция, redaction и отсутствие ложного PASS; явный перечень поддержанных и неподдержанных сценариев | Выполняется после каждого патча; текущий результат v166 — 206/206, py_compile PASS. Это технические fixtures, не готовность произвольного регресса |

## Правила разработки

- STEP/AUTO и v069 action-policy сохраняются. Новый guard добавляет ограничения, не выдаёт разрешений на стендовые изменения.
- Код и архитектура универсальны; продуктовые сведения поступают из наблюдений, stand adapters и валидированных контрактов.
- Перед установкой — резервные копии; затем py_compile, профильные и общие smoke-тесты. Профильный или fixture PASS не называется автономным продуктовым PASS.
- Реальные проверки во время разработки и пилот отдела — разные уровни. Не обещаем закончить всю технику без проверок, но текущий этап можно проверить изолированно без Jira и доступа к новым задачам отдела.
- Разрешение на одну пустую группу уже использовано: группа удалена. Новые ресурсы, команды агентов, существующие объекты и расписания не изменяются без отдельной соответствующей авторизации.
- Jobs, секреты, runtime evidence и резервные копии сохраняются вне Git. Git/GitHub — версия кода, тестов и документации.

## После технического блока

Возвращаемся к реальным задачам отдела, проверяем supported scenarios, выявляем недостающие контракты и расширяем покрытие. Это отладка агента и пополнение проверяемой памяти, а не подразумеваемое обучение весов LLM. Jira подключается отдельным интеграционным этапом после восстановления доступа.
