## Актуальный приоритет: вечерний регресс 15 октября 2026

Новое решение пользователя отменяет текущую очередность коллекции → политики → процедуры: их полная обкатка остаётся в backlog. Сейчас только два выделенных агента Windows и Ubuntu; другие ОС/КЕ не трогаем. Пользователь разрешает обновить именно эти агенты и доставить нужные плагины после проверки идентичности/версий. Версия должна быть подтверждена файлами и текущим UC, а не выбрана как latest. Старое решение о самостоятельном обновлении пользователем ниже — история.

Целевой результат: повторяемый конвейер «проверить агент → при необходимости обновить → проверить/доставить плагины → выполнить заданный кейс → получить свежий результат → expected/actual и PASS/FAIL/BLOCKED». Сценарии пользователь предоставит ссылкой. Источник, включая Jira/Zephyr, используем только для чтения: не менять кейсы, не записывать статусы/комментарии и не подключать write-интеграцию. Сохранить исходные ID, шаги, expected, ОС и revision/hash локального снимка. До получения сценариев допустима техническая подготовка, но не объявление полного покрытия.

### Оптимизированная последовательность и критерии выхода

1. **Один preflight на кампанию.** Зафиксировать ровно два CI/agent ID, ОС/архитектуру, online/last_seen, текущие версии ядра и свежесть plugin audit. Отдельно проверить серверный build catalogue, payload/маршруты текущего UI/OpenAPI, Excel и реальные plugin packages. Каталоги staging UQA и серверное хранилище UC не считать взаимозаменяемыми. Выход: подтверждённая матрица целей и входных файлов, без latest/неизвестной совместимости.
2. **Один общий механизм обновления.** Через поддержанный механизм UC обновить сначала одну выделенную КЕ, проверить возвращение online и фактическую точную версию, затем вторую. Если версия уже нужная — не обновлять повторно. До отправки durable intent, после — binding к task/agent; при timeout сначала reconcile, не resend. Не удалять machine UID, не ставить сырые exe/deb с пустыми config/CA, не менять остальные КЕ.
3. **Одна сверка и доставка плагинов на ОС.** Из кейсов сформировать список нужных plugins × ОС; сопоставить точные версии со справочником и manifests. Уже установлено и loaded нужной версии — skip; отсутствует/устарело — scoped update; более новая версия/неизвестная совместимость — конфликт, не downgrade наугад. После доставки свежий audit того же agent, version/load_status/load_error. ACK не означает установлен/loaded. Не переустанавливать плагины перед каждым case.
4. **Сквозная приёмка одного кейса на обеих ОС.** Выбрать из реальных сценариев короткий репрезентативный безопасный кейс; получить exact inputs/preconditions/expected. UQA сама выбирает поддержанную операцию, отправляет задачу, фиксирует task ID и получает полный результат именно этого запуска. Проверить oracle и отчёт. До этой пары не расширять обещания до всех плагинов; операторское вмешательство отмечать отдельно.
5. **Расширение общим исполнителем, не кодом на каждый кейс.** Разделить повторяемые операции доставки/создания задачи/poll/fetch от plugin-specific inputs и критериев. Параметры и expected брать из проверенного case contract; не сочинять payload/semantics. Для unsupported форматов добавить ограниченный проверяемый adapter; сомнительное сопоставление → BLOCKED. Сначала разные типы результата/режимы задания, затем оставшиеся кейсы тех же типов. Периодические задачи — отдельная очередь с точным расписанием и обязательным прекращением после проверки.
6. **Пакетный регресс Windows × Ubuntu.** Сохранить все ID/шаги/expected исходных кейсов; один результат на каждый применимый case/ОС. Выполнять независимо доступные кейсы при блокере одного плагина; не маркировать непроверенное PASS. Последовательно внутри одной КЕ; параллельность между КЕ допускается только при раздельных сессиях/ресурсах и доказанной изоляции. Не дублировать отправку при рестарте процесса.
7. **Готовые actual для ручного Zephyr.** Case ID, ОС, agent/core/plugin versions, ожидаемое, фактическое, verdict, task ID/time, evidence и ограничение/причина BLOCKED. Привязать фактический результат к каждому ожидаемому критерию. Чужой/старый task, status=success без проверки содержания, HTTP200/ACK и stale audit не дают business PASS. Во внешний источник ничего не писать.
8. **Итог и фиксация опыта.** Coverage matrix и числа PASSED/FAILED/BLOCKED/NOT_RUN, отдельные проблемы UC и ограничения UQA, незавершённые задачи/ресурсы и cleanup. Проверенные переносимые рецепты — в существующую продуктовую память с ОС/версиями/source/evidence и дедупликацией; не хранить дубли сырых ответов как новые знания. Обновить официальную архитектуру/CHANGELOG после завершённого реализованного этапа.

### Ограничение времени

Сначала добиться сквозного кейса на Windows и Ubuntu; это ранняя проверка реальной готовности, не количество fixture smoke. После неё оценить остаток по числу кейсов, времени плагинов и найденным ограничениям. Один инфраструктурный блокер исследовать ограниченным заходом, не тратить часы на одинаковые прогоны или расширение подсказок. Общий набор технических smoke — после связанного code batch; профильные проверки — на изменённых границах. Не ослаблять policy/expected/journal ради дедлайна.

Гарантировать полный регресс к вечеру до чтения сценариев и первого полного update/install/run/fetch нельзя. Проверенный на checkpoint286 результат — несохранённые условия коллекций, чтение historical API schemas и часть agent/plugin read-observation; ещё не автоматическое обновление/доставка/полный plugin regression. Подготовительный код повторно не разрабатывать с нуля: уже есть version reference, distribution catalogue, agent/plugin observers, task/result contracts, journal/ledger и память.

## Цель и границы

Решение пользователя: основной приоритет — снять повторяющиеся ручные действия регресса агента U-Connect на целевых ОС. Начинаем с одного выбранного кейса и расширяем до набора кейсов плагина, затем до матрицы плагинов и ОС. Jira/Zephyr сейчас не подключаем; результат выдаём для ручного переноса. Коллекции, разработка политик и процедур отложены. Готовая политика может позднее служить ограниченным способом подготовки, но массовая установка без проверки scope не выполняется.

Пользователь самостоятельно обновляет ядро агентов. UQA не удаляет machine-uid.txt и не переустанавливает ядро по совету со скриншота. Сообщения разработчика — продуктовые сведения, не разрешение менять существующие агенты или применять массовую политику.

## Последовательность разработки

1. Явный справочник версий: выбранный лист Excel, источник/ячейка/hash; версии плагинов не выводятся из версии ядра.
2. Каталог файлов: checksum, имя, затем проверенные manifest ОС/архитектуры/плагина/версии. Имя файла само по себе не доказывает совместимость.
3. Preflight выбранной КЕ: реальные CI/agent ID, ОС/архитектура, версия ядра, online и свежий plugin audit.
4. Подготовка одного плагина: точная версия уже loaded — не переустанавливать; отсутствует/старее — ограниченная установка; версия новее справочника — конфликт, не автоматический downgrade. Обычная action-policy остаётся.
5. Подтверждение загрузки: свежий audit того же агента, версия и состояние; upload ACK недостаточно.
6. Один кейс: пользователь задаёт параметры, preconditions и ожидаемый результат. Пустой expected не превращается в критерий «ответ есть».
7. Запуск: точные агент/плагин/параметры, durable intent до отправки и доказанный task ID. Timeout не разрешает слепой повтор.
8. Получение результата: native fetch/GET того же task/agent, время данного запуска, завершённость; чужие и старые ответы не принимаются.
9. Отчёт: каждый критерий, ожидаемое/фактическое, PASS/FAIL; BLOCKED отдельно для отсутствующих preconditions/evidence. Бизнес-вердикт не назначается только моделью.
10. Несколько кейсов одного плагина: изоляция параметров/ресурсов, restoration/cleanup, отсутствие дубликатов после рестарта.
11. Матрица плагинов × ОС: supported/unsupported/dependency, отдельный результат каждой ячейки, сводка без ложного общего PASS.
12. Пилот отдела и демонстрация реальных результатов руководителю. Jira-интеграция — отдельный следующий этап.
