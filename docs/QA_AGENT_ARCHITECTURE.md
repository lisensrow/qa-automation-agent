# Архитектура QA-агента UQA

Статус документа: живое описание текущей архитектуры. Обновляется вместе с изменениями UQA.

Аудит 14 октября 2026: описанные successful сценарии не означают готовность всего frontend или завершение 12-stage цели. Два первоначальных demo Jobs прошли штатный runtime без экспериментального ограничителя; для следующего показа созданы новые read-only Jobs в состоянии created/pending без старых evidence/verdict. Их подготовка/запуск описаны в UQA_PILOT_READINESS.md. Live owned-resource lifecycle/recovery и обратная связь реального отдела ещё отсутствуют. Демонстрационный пакет — самостоятельный подготовленный материал, не состоявшаяся пилотная приёмка.

## Что умеет агент

- Штатный runtime, без дополнительного экспериментального scope harness, выполнил demo Jobs exact карточки Ubuntu и Agent Windows: 20261014-003656-0c45b6f4 / 20261014-003656-f2629931 PASS 3/3, без операторской навигации и WRITE подтверждений, resources=0. Это ограниченное подтверждение обычного пути исполнения, не всех frontend-функций.

- Загружает индексированный факт о навигации Agent с проверкой текущих architecture/backend/frontend и подтверждает его новым UI-наблюдением. Три реальных Jobs PASS 3/3, loaded_fact_count=1, navigation/fact_reconfirmation=runtime_confirmed, evidence_for_pass=false. UI/API binding этим прогоном не подтверждался; веса модели не обучались.

- Подтверждённо читает exact карточку и вкладку Agent у Ubuntu и Windows КЕ: четыре свежих prepared corpus Jobs PASS 3/3. Это доказательство выбранных UI-проверок, не свежести телеметрии, работоспособности задач или всех вкладок.

- Сохраняет доступность схем чтения и навигации, объявленных полным валидным locked check-контрактом, при переключении progressive catalog. Это не исполнение инструментов и не разрешение действий: каждый вызов проходит прежнюю policy. Неполный или неподтверждённый контракт ничего не загружает.

- Выполняет проверенный form open/read/close сценарий Add → Add group → Escape без ввода/сохранения. Реальный Job 20261013-235806-b2f1b56f PASS 3/3: native controls 7→9→7, все критерии повторно вычислены из evidence текущим оценщиком. Это узкий сценарий, не готовность всех форм или мастеров.

- Проверяет декларативный жизненный цикл поверхности формы по связанным наблюдениям: исходное состояние, подтверждённое открытие, новые активные native controls, подтверждённое Escape и восстановление исходного состояния. Без полного доказательства не принимает модельный PASS. Это проверенный механизм оценки, а не уже доказанная автономность любых форм.

- Выполняет подготовленный bound filter roundtrip в CMDB: заполняет разрешённое поле, читает поле/таблицу, очищает то же поле и проверяет восстановление. Три независимых реальных Jobs подряд дали PASS 4/4 без операторской очистки. Это ограниченный проверенный сценарий, не универсальная готовность frontend и не подтверждение памяти/API.

- Сохраняет валидный полный контракт prepared frontend-сценария от материализации Job до запроса модели; не заменяет его на null при текстовой компиляции. Это не разрешение изменений и не авторитет для произвольного плана LLM.

- Останавливает повтор идентичного отсутствующего semantic click на неизменившейся странице до нового исполнения/подтверждения. Изменение наблюдаемого состояния допускает переоценку через обычную policy, не автоматический повтор.
- Сохраняет типизированные счётчики и флаги аудита валидации полей, подписей и диалогов отдельно от обрезанного текстового evidence. Значения полей не копируются в этот факт; нулевое число полей не доказывает открытие формы.
- Сохраняет явно заданный пользователем узкий критерий «ровно одна видимая строка» независимо от перефразирования планировщиком; проверяет фактический count через locked контракт. Если все критерии активного read-only case имеют пригодные доказательства, завершает его без дополнительных действий модели. Это не универсальный компилятор произвольных требований.
- Понимает QA-запрос на естественном языке и превращает его в проверяемый план.
- Может явно загрузить проверенные UI/API-факты из продуктовой памяти в контекст модели; для frontend-aware режима требует отдельного runtime confirmation текущих architecture/backend/frontend. Память — подсказка для нового прогона, не доказательство PASS и не обучение весов LLM.
- Накапливает знания о точной навигации «строка таблицы → карточка → именованные вкладки» отдельно от UI/API bindings. После двух разных успешных Jobs текущего frontend может подставить этот факт модели и заново подтвердить его наблюдениями Core; имя/ID конкретной машины в общий навигационный факт не попадают.
- Отличает одиночный последовательный сценарий от набора независимых test case.
- Материализует готовый сценарий продуктового корпуса в один persistent regression Job и запускает этот же Job командой `/run-job JOB_ID` без повторного LLM-планирования. Повторная материализация того же активного сценария, стенда, bindings и набора checks возвращает существующий Job вместо создания дубликата.
- Fail-closed отделяет `ready` продуктовые сценарии от `candidate` и `blocked_external`; каждый candidate обязан хранить явную проверяемую причину, что именно ещё мешает реальному прогону.
- Показывает список последних Job через `/jobs` и безопасную структуру выбранного Job через `/job JOB_ID`: только статусы, идентификаторы, стенд, счётчики cases/checks/evidence/observations/resources и cleanup-state, без исходного запроса, summary, названий ресурсов и содержимого результатов или evidence.
- Показывает активную подготовленную очередь через `/queue`: только Job/source case ID, стенд, Job/case status, число planned checks и время обновления; task, bindings, checks, evidence и observations не выводятся.
- Нормализует planner checks в уникальные стабильные `planned-*` ID; повторённый моделью ID не может слить разные критерии в один результат.
- Выполняет UI-проверки в браузере по смысловым названиям элементов, а не по хрупким координатам.
- Выбирает значения native select и ARIA combobox по точным видимым именам без ручного угадывания option.
- Идемпотентно устанавливает checkbox/switch в требуемое состояние и не переключает уже правильное значение.
- Выбирает radio option внутри точной именованной группы и устанавливает точный набор в native или ARIA multi-select, включая chip-based combobox.
- Работает с поисковым ARIA autocomplete: вводит точный запрос и выбирает единственную совпавшую option.
- Устанавливает canonical значения native date/time/datetime-local/month/week, заранее проверяя min/max/step и подтверждая фактическое value после изменения.
- Устанавливает точное значение native range или ARIA slider через bounded keyboard steps с проверкой min/max/step и итогового значения.
- Читает структуру ARIA tree и идемпотентно раскрывает/сворачивает точный узел с проверкой aria-expanded.
- Идемпотентно выбирает или снимает точный treeitem при явном aria-selected/aria-checked, не нажимая Save.
- Открывает, осматривает и закрывает popup, однозначно связанный с точной кнопкой через aria-controls, без Apply/Save.
- Читает параметры file input и выбирает только встроенный безопасный текстовый fixture, не получая произвольного пути к файлу на сервере.
- Захватывает ожидаемое скачивание, сверяет имя, сигнатуру формата и при известном SHA-256 содержимое, не возвращая сам файл модели.
- Сопоставляет статус КЕ в открытой карточке с CI/agent API и свежестью CPU/RAM-телеметрии из ответов этого же веб-интерфейса; противоречия не выдаёт за PASS.
- Проверяет аудит плагинов выбранного агента по наблюдённому GET-ответу: точное имя, версия, состояние загрузки и давность аудита. PASS чтения старого отчёта не является PASS его свежести или здоровья агента.
- В подготовленных read-only сценариях независимо проверяет связь CI/agent/sample/audit по фактическим ID, наличие статусов, точного плагина, версии и времени обновления; сохраняет возраст и признак freshness без ослабления порогов. Отсутствующие/чужие данные блокируют только зависимые checks.
- Для полностью покрытого машинными контрактами read-only observation workflow Core сам формирует набор итоговых checks после попытки заданного observer; модель выполняет навигацию, но не должна генерировать JSON итогового вердикта. До сверки доказательств все такие checks BLOCKED.
- Проверяет наличие конечных числовых CPU/RAM/uptime значений в прочитанном monitoring sample, включая диапазон явного RAM percent. Это чтение измерений, а не проверка отрисовки графиков, нормальной нагрузки или текущей свежести.
- Для отдельной read-only проверки плагина Core задаёт последовательный маршрут `точная строка КЕ → карточка → Agent → Plugins → plugin inspector`; без ожидаемой версии возвращается наблюдённая версия, а запуск или обновление аудита не выполняется.
- Читает список задач выбранного агента по уже наблюдённому GET, показывает только безопасные метаданные и не принимает статус задачи за проверенный вывод её выполнения.
- Core отдельно отличает ненаблюдавшийся GET списка от отсутствующей задачи и принудительно формирует BLOCKED-check из сохранённого наблюдения, если модель утверждает обратное.
- Если точной задачи нет, показывает ограниченный набор увиденных имён и блокирует повтор той же инспекции без нового ответа сервера.
- Повторяющиеся имена задач различает по точному ID из уже наблюдённого GET; одновременно указанные имя и ID должны совпасть у одной записи.
- Для точно идентифицированной задачи читает штатный GET `/full` и сообщает только наличие результата, его тип, время обработки и код ошибки. Сам вывод, параметры и текст ошибки не передаёт модели; такой снимок ещё не доказывает корректность выполнения.
- Может проверить, содержит ли закрытый текстовый результат ожидаемую строку и совпадает ли код ошибки, но только если точное ожидание явно присутствует в исходном пользовательском Job. В evidence сохраняются hash и длина ожидания, а не сам вывод; Core самостоятельно формирует PASS/FAIL.
- Для явно запрошенной periodic-проверки сохраняет приватный baseline той же пары agent ID/task ID и подтверждает второй запуск только по более новому валидному `processed_at`. Одинаковый timestamp остаётся BLOCKED; содержимое результатов не сохраняется.
- Создаёт безопасную `executeCommand`-фикстуру только из закрытого allowlist: модель не может передать программу, shell, `sudo` или произвольные аргументы. Ожидаемый маркер остаётся приватным, а Core получает только hash и итог совпадения.
- Перед созданием managed agent task повторно проверяет точную КЕ через Core-owned телеметрию и допускает WRITE только при совпавшем имени, статусе online во всех источниках и свежем monitoring; иначе завершает сценарий как BLOCKED без POST.
- Выбирает отдельный закрытый marker-профиль для Linux/Unix или Windows и до создания задачи сверяет его с наблюдённым `os_name` КЕ; несовместимый или неизвестный профиль блокируется до POST.
- Автоматически и в том же tool-flow регистрирует созданную agent task в persistent resource ledger. После сбоя Cleanup Manager может восстановить точный task ID и отключить задачу без приватного маркера.
- Для текущего U-Connect, где API удаления agent task отсутствует, применяет явный cleanup-контракт `PUT enabled=0` и принимает cleanup только после повторного `GET`, подтвердившего точные agent ID/task ID/name и `enabled=0`.
- Сохраняет телеметрию агента и аудит плагинов как два независимых структурированных наблюдения; Core выводит их статусы из собственных результатов инструментов и не переносит дату аудита в проверку телеметрии.
- Переносит тестовый пакет из ограниченного каталога сохранённого стенда в закрытую область текущего Job только после проверки SHA-256; выбирает его в браузере по artifact ID, а не по пути из ответа модели.
- Проверяет фактический Tab focus order, выполняет закрытый набор keyboard chords и тестирует copy/paste через изолированный session-private clipboard без доступа к системному буферу.
- Перетаскивает точный semantic source на точный target, проверяет итоговый порядок и отдельно подтверждает его сохранение после повторной загрузки.
- Получает структурированный снимок таблицы, управляет сортировкой, выбором точной строки и проверяемой пагинацией.
- Открывает точную строку таблицы по её ячейке только после уникальной инспекции на той же странице и повторной проверки уникальности непосредственно перед кликом.
- Может выполнить единый read-only workflow `точная строка → карточка деталей`: требует ровно одну строку, открывает только её, сохраняет тот же origin и машинно подтверждает identity карточки по heading, title, смене URL с точным видимым именем либо доказанному увеличению числа точных видимых экземпляров имени в in-place drawer/panel. Неоднозначность или недоказанная identity дают `BLOCKED`, а не предполагаемый PASS.
- Может атомарно продолжить этот workflow проверкой явно заданного списка ARIA-вкладок: каждую вкладку находит и нажимает по точному имени, после чего требует ровно одну выбранную вкладку, совпадение её имени с запросом и видимую panel, связанную через `aria-controls`. Проверяются свойства выбранной вкладки, поэтому допустим интерфейс с ленивым созданием только активной panel; смена origin или неоднозначность дают `BLOCKED`.
- Проверяет одну точно именованную форму без ввода и отправки: собирает обязательные поля, требует доступные labels, проверяет ссылки `aria-labelledby`/`aria-describedby`, при заданном ожидании сверяет точный набор required-полей и отдельно доказывает отсутствие POST/PUT/PATCH/DELETE в окне инспекции. Результат принадлежит Core и не может быть заменён предположением модели.
- Выполняет замкнутую проверку точного text/search-фильтра таблицы: сохраняет исходное значение и строки, применяет фильтр, проверяет значения указанной колонки и согласованность reported total, затем в обязательном cleanup-блоке возвращает исходный фильтр и ждёт восстановления сигнатуры строк. Отсутствующий total даёт `BLOCKED`, но не мешает восстановлению UI.
- Выполняет замкнутую проверку пагинации таблицы: фиксирует current page, visible range, total и сигнатуру строк, переходит одной точной соседней кнопкой, затем в обязательном cleanup возвращается точной обратной кнопкой и доказывает исходную страницу и строки. Disabled control блокируется до клика; persistent selection ledger явно не считается продуктовым evidence.
- Выполняет замкнутую проверку сортировки одной точной колонки: требует наблюдаемый `aria-sort`, проверяет фактическую монотонность значений и затем возвращает исходное направление и сигнатуру строк. Если исходное состояние было несортированным, восстановление выполняется безопасной перезагрузкой той же страницы с проверкой origin и row identity.
- Для принадлежащей текущему Job одноразовой fixture выполняет единый WRITE-workflow изменения text-like поля: приватно фиксирует baseline всей точной формы, доказывает dirty-state, нажимает единственную exact Save-кнопку, перезагружает тот же origin и проверяет persistence нового значения и неизменность всех остальных наблюдавшихся полей. Значения и baseline не возвращаются модели; scope предварительно ограничен resource ledger allowlists и v069 policy.
- Детерминированно открывает задачи точной КЕ по наблюдаемому пути `строка КЕ → Agent → Tasks`; на каждом этапе требует единственное точное совпадение и подтверждает, что наблюдённый список задач относится к тому же агенту.
- После точного открытия вкладки `Tasks` ограниченно ждёт именно связанный GET списка задач, устраняя гонку интерфейса и сети; ожидание не повторяет клики и не допускает WRITE.
- Если офлайн-агент не инициирует GET списка задач, подтверждённые точная КЕ, agent ID и выбранная вкладка разрешают только переход к readiness-check; создание fixture без task-list anchor по-прежнему невозможно.
- Сохраняет выбранные строки одной таблицы между страницами пагинации в persistent ledger и отдельно показывает полный набор выбора, не запуская bulk action.
- Применяет column filters, управляет select-all и проверяет bulk-action preview без запуска массовой операции.
- Работает с filter popovers и отличает число видимых строк от server-side total/range/current page.
- Снимает fingerprint фактических UI-контрактов, сохраняет историю по Job и обнаруживает смену совместимых adapters между прогонами; несовместимый контракт блокирует WRITE/DESTRUCTIVE до исполнения.
- Связывает видимую метку формы с единственным соседним полем даже в интерфейсах с неполной accessibility-разметкой.
- Если точная инспекция элемента доказала ошибочность предположенной роли, следующий клик по тому же имени на той же странице может использовать проверенный текстовый fallback; без такой инспекции роль остаётся строгой.
- Если модель после точной инспекции меняет предположенную роль или повторяет имя цели как container, Browser Runtime всё равно допускает только единственный видимый exact-match на том же URL; иной container не отбрасывается.
- Для managed безопасной навигации Core может однократно повторить неисполненный клик, если модель указала self-container и неподтверждённую роль: повтор идёт только по точному уникальному имени. WRITE/DESTRUCTIVE и другой container автоматическому повтору не подлежат.
- Повтор точной неуспешной инспекции блокируется только на неизменной странице; после успешного перехода к другому разделу поиск разрешён заново.
- Повтор одинакового read-only снимка таблицы или точной строки на неизменившейся странице останавливается Core до повторного browser-вызова; после доказанного изменения URL или содержимого страницы та же инспекция снова разрешена.
- Умеет проверять ожидаемый результат и выносить итог `PASS`, `FAIL` или `BLOCKED` по фактическим данным.
- Не считает клик или отправку формы доказательством успеха: требуется последующая runtime-проверка результата.
- Собирает evidence и observations по каждому test case и хранит их вместе с QA Job.
- Разделяет безопасное наблюдение, обычное взаимодействие, запись и разрушительные действия.
- Сохраняет действующую policy v069: чтение и безопасная навигация выполняются автоматически, изменения и destructive-действия проходят через policy.
- Явный глобальный маркер `read-only/read only/readonly/только чтение` имеет fail-closed приоритет над перечисленными внутри запрета словами Add/Create/Edit/Save/Delete; такие перечисления не могут случайно включить WRITE.
- Поддерживает режимы STEP и AUTO без изменения их базовой архитектуры.
- Запоминает созданные тестовые ресурсы на диске в persistent resource ledger, поэтому cleanup можно продолжить после сбоя процесса или модели.
- Перед редактированием тестовой fixture проверяет точный resource ledger scope: ресурс должен принадлежать текущему Job, быть активным и одноразовым, иметь обязательный cleanup-контракт, а поле и новое значение — входить в заранее сохранённые exact allowlists. Эта проверка ничего не меняет на стенде и не считается product evidence.
- Выполняет cleanup только для точного ресурса из ledger и проверяет результат по семантике операции: исчезновение после DELETE или подтверждённое архивное состояние после archive.
- Умеет восстанавливать безопасный путь навигации до ресурса по наблюдениям, не повторяя исходные Create/Add/Save-действия.
- Восстанавливает стартовый URL cleanup из подтверждённого browser observation, когда стенд не был записан в текст Job.
- Не разрешает generic Add/Create только на основании любого перехода: открытая страница должна семантически соответствовать целевому типу ресурса.
- Не принимает документированный API endpoint за UI-маршрут: первый не подтверждённый deep link открывается с корня стенда и продолжается через фактически видимую навигацию.
- Поддерживает универсальный UI-cleanup и metadata-driven REST-cleanup без привязки Resource Manager к типам сущностей U-Connect.
- Учитывает зависимости ресурсов и очищает дочерние объекты раньше родительских.
- Регистрирует продуктовые blocker отдельно от ошибок агента и сохраняет версии компонентов, на которых blocker подтверждён.
- Автоматически сверяет версии backend/frontend выбранного стенда с версиями открытых blockers и переводит blocker в состояние повторной проверки при изменении версии.
- Не отправляет SSH-пароли и сохранённые учётные данные модели; работа с ними отделена от LLM-контекста.
- Перед созданием нового Job проверяет не только HTTP-доступность Ollama и наличие настроенной модели, но и выполняет ограниченный реальный inference warmup. Успешная готовность кешируется на короткое время; timeout или отсутствие модели сбрасывают кеш и останавливают запрос до появления пустого Job.
- Отклоняет managed HTTP(S) URL со встроенными `user@host` или `user:password@host` как из текста задачи, так и из Stand Store; такие данные не передаются модели и не используются для браузерного перехода.
- Для managed workflow предпочитает сохранённый `web_url` уже разрешённого стенда любому URL, который модель могла извлечь из текста; текстовый URL остаётся fallback только для неизвестного стенда.
- Нормализует конечную пунктуацию после exact CI и fallback URL, поэтому двоеточие или точка обычного предложения не становятся частью идентификатора.
- На каждом pre-create шаге managed workflow машинно сверяет фактический browser origin с разрешённым origin из Stand Store: после открытия страницы, маршрута к КЕ/Tasks, capability probe и telemetry. Другой host, scheme или port, похожий поддельный домен и отсутствие фактического URL завершают сценарий `BLOCKED` до любых мутаций.
- До первого сетевого перехода managed workflow сверяет origin URL, предложенного моделью, с разрешённым Stand Store origin. Попытка открыть другой host, scheme или port блокируется Core до выполнения `browser_open_page`.
- Стартовый managed-переход разрешает только точный entry URL из Stand Store с теми же path/query/fragment; произвольный same-origin путь вроде `/logout` не выполняется. После открытия допустим штатный same-origin redirect стенда.
- Формирует и накапливает продуктовые наблюдения и candidate facts для дальнейшего расширения базы знаний.
- Архитектура базы знаний допускает масштабирование через нормализованные наблюдения, кандидаты, проверку конфликтов и продвижение подтверждённых знаний, а не через бесконтрольное накопление текста диалогов.
- Ограничивает объём browser state, передаваемый модели, сохраняя приоритет для menu items, полей ввода, кнопок и навигации; исходный result остаётся доступен evidence/observation pipeline.
- Имеет отдельный декларативный продуктовый корпус ручных U-Connect frontend-задач вне Core: 17 сценариев в 6 категориях с prerequisites, checks, readiness, action profile, policy и cleanup requirements. Наличие сценария/ready не является доказательством его PASS на стенде.

## Назначение и границы

UQA — универсальный QA-агент для выполнения регрессионных и диагностических сценариев на выбранном тестовом стенде. Ядро управляет планом, policy, доказательствами и состоянием задания. Модель выбирает следующий осмысленный шаг только внутри набора инструментов и ограничений, которые передало ядро.

Resource Manager не содержит ветвлений по конкретным сущностям U-Connect. Для него пользователь, зона, политика или запись — это тестовый ресурс с типом, именем, внешним идентификатором, состоянием, зависимостями и metadata.

Product adapters могут записывать в универсальную metadata именованный cleanup-контракт. Resource Manager хранит его как данные; конкретное выполнение остаётся в ограниченном adapter-инструменте и проходит общую policy v069.

## Основной поток выполнения

1. UQA принимает запрос и определяет целевой стенд.
2. Planner создаёт один или несколько test case. Последовательный workflow остаётся одним case с несколькими checks.
   Core удаляет служебные meta-checks и детерминированно заменяет пустые или повторяющиеся `check_id`, сохраняя порядок и отдельность критериев.
3. Для каждого case агент выполняет наблюдения и действия через разрешённые инструменты.
4. Core классифицирует каждое действие и применяет policy до исполнения.
5. После каждого значимого шага сохраняются evidence и observations.
6. Созданный тестовый объект немедленно регистрируется в resource ledger.
7. Verdict строится по фактическим checks: `PASS`, `FAIL` или `BLOCKED`.
8. Cleanup Manager получает pending-ресурсы, очищает их в безопасном порядке и сохраняет каждую попытку.
9. Подтверждённая невозможность cleanup на стороне продукта регистрируется как product blocker.

## Компоненты

### UQA Core

Главный координатор. Хранит диалоговый контекст, запускает planner и test cases, выдаёт модели инструменты, применяет action-policy, записывает результаты и запускает cleanup.

Artifact Staging — отдельный Job-scoped поток для разрешённого тестового пакета. Источник ограничен `uqa-input` SSH-пользователя выбранного стенда; путь проверяется без traversal и symlink-алиасов, размер ограничен, SHA-256 обязателен. Пакет хранится с закрытыми правами и повторно хешируется перед выбором в браузерном file input/chooser. Выбор файла считается WRITE и не является доказательством загрузки или развёртывания на сервере. STEP/AUTO и policy v069 не меняются.

Ключевые обязанности:

- выбор и фиксация стенда;
- отделение credentials от модельного контекста;
- управление STEP/AUTO;
- классификация действий;
- исполнение tool call через policy;
- проверка полноты и качества verdict;
- координация ledger и Cleanup Manager;
- показ статуса и открытых product blockers.

Navigation Resolver использует задачу, локальную документацию и только фактически видимые navigation labels. Для иерархических меню он выбирает ближайшую смысловую категорию, затем переоценивает вновь открывшиеся пункты. Если открытая страница не соответствует целевому понятию, Core продолжает требовать навигацию и не передаёт generic Add/Create в mutation policy.

Для часто повторяемого пути к задачам агента Browser Runtime предоставляет составной semantic route: точная строка КЕ в текущей таблице, точная вкладка `Agent`, затем точная вкладка `Tasks`. Маршрут не содержит координат и жёстко заданного URL, прекращается при первом неоднозначном или отсутствующем элементе и после перехода связывает наблюдённый task-list с исходной КЕ. Модели возвращается компактный результат без полного DOM и сетевых payload. Этот инструмент относится к `INTERACT`, не изменяет стенд и сам по себе не является evidence для PASS.
После клика по точной вкладке `Tasks` runtime до трёх секунд опрашивает только уже захваченные GET-ответы текущей browser session. Он не повторяет навигационные клики и не отправляет отдельные запросы к продукту. Успех принимается лишь при совпадении точного agent ID из наблюдения КЕ и endpoint списка задач; timeout остаётся `BLOCKED`.
Исключение ограничено офлайн-preflight: если UI действительно выбрал `Tasks`, точная КЕ и agent ID уже связаны наблюдёнными GET, но сам frontend не запросил task-list, маршрут возвращает `ready_for_readiness`. Это разрешает только Core-owned telemetry check. Инструмент создания по-прежнему требует ранее наблюдённый same-origin task-list endpoint и без него не выполняет POST.

В managed-agent Job Core извлекает явно обозначенное точное имя КЕ из авторитетного текста Job и устанавливает route lock ещё до первого browser-действия. До открытия пользовательского стенда разрешён только `browser_open_page`; после него — только `browser_open_agent_tasks_semantic` с тем же именем. Успешная точная инспекция единственной строки также может установить lock как дополнительный fallback. Если модель пытается закончить case, Core продолжает цикл и повторно выдаёт точный обязательный tool call. Это не позволяет языковой модели уйти в Administration или создание distribution package.

После открытия `Agent → Tasks` Core продолжает managed lifecycle как конечный автомат: capability probe, обязательный readiness-check точной КЕ, точный managed create и затем только проверка закрытого результата созданного task ID. Readiness-check требует Core-owned evidence, совпавшее имя КЕ, `online` во всех доступных источниках и свежий monitoring. При `BLOCKED` lifecycle сразу переходит к verdict и POST создания задачи не выполняется. Generic `Create task`, повторная ручная навигация и другой task ID блокируются до исполнения. При незавершённой фазе модель не может преждевременно вернуть финальный ответ.
Если составной маршрут не находит единственную строку КЕ или одну из обязательных вкладок, Core сохраняет первый результат, очищает общий navigation-lock и немедленно переводит workflow в `verdict`. Повтор того же маршрута и любые альтернативные tool calls блокируются; ошибка навигации становится `BLOCKED`, а не циклом обращений к модели.
После проверенного результата workflow переходит в фазу `verdict`: новые tool calls модели блокируются, включая повторную регистрацию ресурса и ручной disable. Регистрацию уже выполнил Core после create, а cleanup остаётся обязанностью Cleanup Manager.
Успешные route, create и финальная проверка сбрасывают устаревшие generic navigation/constrained preflight-маркеры, чтобы после уже подтверждённого результата модель не возвращалась к повторным кликам Agent/Tasks.

Первое открытие браузера в managed case имеет отдельную защиту: глубокий URL разрешается без нормализации только когда пользователь указал его дословно. Иначе Core открывает origin того же стенда. Это не даёт модели превратить найденный API endpoint или придуманный `/app/...` в непроверенный UI-маршрут.
Если Job уже содержит `stand`, Core повторно разрешает его через Stand Store и передаёт managed workflow точный сохранённый `web_url`. Это правило имеет приоритет над первым URL из текста Job и не раскрывает credentials; fallback к тексту применяется только при отсутствии сохранённого стенда или валидного HTTP(S) `web_url`.

### Planner

Преобразует пользовательскую задачу в исполнимые test cases и checks. Планировщик должен сохранять причинно связанную последовательность действий внутри одного case. Несколько независимых целей могут быть разделены на разные cases.

Если пользователь явно задаёт «один последовательный test case» или эквивалентную формулировку, Core нормализует даже ошибочно разделённый LLM-план обратно в один case, перенося этапы в checks.

Planner также возвращает для каждого case внутренние `case_key`, `workflow_key` и `depends_on`. Core строит по ним группы зависимостей до создания Job: cases с общим состоянием или прямой зависимостью объединяются в один исполнимый workflow, а их критерии становятся checks. Независимые cases без общей группы остаются раздельными. Эти служебные поля не попадают в итоговый пользовательский план и не меняют STEP/AUTO или action-policy.

Для managed agent lifecycle модельный план не считается авторитетным контрактом. Если запрос содержит точную КЕ и allowlisted fixture, Core заменяет произвольный набор критериев одним case с шестью обязательными checks: readiness, exact agent binding, private marker result, persistent ledger registration, Cleanup Manager completion и подтверждённое `enabled=0`. Это исключает придуманные, дублирующие и противоречивые проверки, сохраняя пользовательское подтверждение плана, STEP/AUTO и policy v069.

Явная граница пользователя имеет более высокий приоритет, чем метаданные модели: формулировки «ровно N независимых test case» и «не объединяй» запрещают Core coalescing, даже если planner ошибочно присвоил cases общий `workflow_key`. Это защищает отдельные Windows/Ubuntu, роли, страницы и другие независимые цели от повторного склеивания.

Planned checks связываются по Core-owned `planned-*` ID. Если модель сохранила точные уникальные заголовки, но заменила только IDs своими `check-*`, Core может восстановить соответствие один к одному по нормализованному точному title. Неоднозначные, неполные и приблизительные совпадения по-прежнему блокируются.

Для простых semantic UI-требований Core заранее фиксирует machine-readable assertion и сам вычисляет PASS/FAIL по связанному DOM-наблюдению. Библиотека поддерживает видимость, доступность, редактируемость, checked/selected/expanded, required/invalid/read-only, а также точное или частичное сравнение value/text. Контекстные требования вида «после сохранения» намеренно не упрощаются до одного boolean: без доказанного предусловия они остаются BLOCKED, а не превращаются в ложный PASS. Ограничения выполнения «в режиме read-only» / `mode read-only` также не компилируются как свойство UI-элемента.

После Core-owned telemetry observation со статусом PASS/BLOCKED и сохранённым evidence Core требует немедленный structured verdict. Повтор того же telemetry-tool для той же КЕ не выполняется, даже если модель меняет freshness threshold; после повторного игнорирования директивы case завершается BLOCKED вместо расходования всего tool-step лимита.

Одно составное telemetry observation разрешено использовать для нескольких заранее запланированных проверок только при однозначной связи с одним Core evidence. Core разворачивает общий ответ модели по исходным `planned-*` идентификаторам и независимо проверяет online-статус, наличие CPU sample и наличие RAM sample. Названия и expected из плана сохраняются; отсутствие конкретного числового показателя даёт `BLOCKED`, а не общий ложный PASS.

Для явного read-only запроса телеметрии Core заранее задаёт короткий маршрут `CMDB → exact row inspection → exact role=row click → telemetry observation → verdict`. Create/edit controls и лишняя пагинация исключаются из маршрута; v069 policy остаётся последним обязательным защитным слоем, если модель всё же запросит WRITE.

После открытия CMDB, подтверждения точной строки и после её открытия Core повторно выдаёт только следующий допустимый шаг маршрута. Это не заменяет семантические проверки инструментов, но не даёт малой модели уйти в create-flow или потерять цель и многократно перечитывать уже подтверждённую таблицу.

### Action Policy v069

Policy — обязательный шлюз между намерением агента и фактическим действием.

Create-иконки с semantic name `plus` или `+` классифицируются как WRITE так же, как Add/Create. Это закрывает обход read-only policy через безымянную кнопку открытия create-flow.

Создание managed agent task классифицируется как `WRITE`, а её отключение — как `DESTRUCTIVE`. Read-only проверка закрытого результата остаётся `OBSERVE`. Эти действия не обходят существующий шлюз и не меняют STEP/AUTO.

### Managed Agent Task Lifecycle

Профиль `posix_printf_marker_v1` использует фиксированную программу `/usr/bin/printf`. Профиль `windows_cmd_echo_marker_v1` использует фиксированный `C:\Windows\System32\cmd.exe` и фиксированный префикс аргументов `/d /s /c echo`. Runtime сам добавляет одноразовый маркер последним аргументом. Tool schema принимает только `ci_name` и идентификатор профиля; полей для произвольной команды или аргументов нет. До POST профиль сопоставляется с наблюдённым `os_name`, поэтому Windows-профиль нельзя запустить на Linux/Unix и наоборот.

После HTTP 201 Core немедленно добавляет ресурс `agent_task` с точным task ID, agent ID, именем КЕ, fixture ID и cleanup-контрактом. Маркер и вывод команды в Job не записываются. Проверка `/full` нормализует обе наблюдавшиеся формы envelope: legacy `result/error_code` и текущую `data.stdout/data.stderr/data.errorlevel`. Затем она сравнивает закрытый stdout с session-private маркером и возвращает только структурированные booleans, код ошибки, timestamp и hash ожидания.
Для задачи, только что созданной managed adapter, `/full` читается по точному task ID из приватного session registry и не ждёт, пока UI-пагинация списка задач начнёт показывать новую запись. Origin и agent ID по-прежнему связываются с наблюдённой КЕ; произвольный task ID этим путём недоступен.
Managed-проверка выполняет до шести read-only запросов `/full` с интервалом пять секунд и прекращает polling сразу после появления проверяемого результата. Ожидание ограничено тридцатью секундами одного tool call и не расходует отдельные LLM tool steps.

В backend 4.9.0 для `/agents/{agent_id}/tasks` доступны create/read/update, но отдельного delete route нет. Поэтому cleanup adapter сначала повторно проверяет identity задачи, выполняет `PUT {"enabled": 0}`, затем читает ту же задачу через GET. Только `post_disable_verified=true` позволяет Cleanup Manager отметить ресурс `cleaned`; повторный cleanup уже отключённой задачи идемпотентен.

Для cleanup-контракта `agent_task_disable_v1` Cleanup Manager не воспроизводит накопленный generic navigation trace. После сброса browser context он открывает сохранённый стенд, вызывает точный составной маршрут КЕ `Agent → Tasks`, а затем exact disable adapter с task ID из ledger. Для остальных типов ресурсов общий механизм replay остаётся прежним.

Навигационный preflight для generic Add/Create предлагается только при положительном намерении создать объект. Read-only Job, даже с просьбой сохранить evidence, не получает принудительный маршрут через меню создания; если целевая КЕ уже видна, агент может открыть её напрямую.

Классы действий:

- `OBSERVE` — чтение состояния без изменения;
- `INTERACT` — безопасная навигация и раскрытие интерфейса;
- `WRITE` — создание или изменение данных;
- `DESTRUCTIVE` — удаление, архивирование и иные разрушительные изменения;
- `UNKNOWN` — действие, которое нельзя безопасно классифицировать.

Глобальный read-only detector не должен блокировать явно запрошенный managed workflow только потому, что рядом присутствует ограничение «не изменять существующие объекты».

### Browser Tools

Браузерный слой открывает страницы, возвращает состояние интерфейса и сети, находит элементы по семантике, заполняет поля, выбирает варианты в dropdown/combobox, устанавливает checkbox/switch и выполняет клики. Для табличных ресурсов поддерживается выбор точной строки и её context menu.

Операции выбора и установки состояния относятся к WRITE и проходят через тот же action-policy v069, что и заполнение обычных полей; read-only задачи блокируют их до исполнения. Native `select` изменяется только при единственном совпадении видимой option. ARIA combobox раскрывается и принимает только единственную видимую option. Уже выбранное значение native select и уже установленный checkbox/switch сохраняются как `already_satisfied` без повторной мутации.

Обязательные field/value constraints теперь направляют модель одним атомарным вызовом `browser_select_semantic`. Успешный вызов регистрирует выполненную пару field/value в Core, поэтому последующий Save не заставляет агента повторно раскрывать поле и вручную угадывать role option.

Radio primitive сначала сужает поиск именованной группой через `radiogroup`/group либо `fieldset/legend`, затем требует единственную option. Multi-select primitive до мутации проверяет существование и однозначность всего запрошенного набора и после изменения сверяет полный фактический набор. Он поддерживает native `select[multiple]`, постоянный ARIA listbox с `aria-multiselectable=true` и составной combobox/listbox, где выбранные значения отображаются chips. Лишнее выбранное значение снимается только через его точную ARIA option; отдельная кнопка удаления по приблизительному тексту не угадывается. Для ARIA autocomplete одиночный selection primitive может ввести поисковое значение в combobox, дождаться option и выбрать её в рамках одного policy-controlled действия.

Temporal primitive работает только с нативными HTML `date`, `time`, `datetime-local`, `month` и `week`. Значение передаётся в canonical HTML-формате. Перед мутацией runtime проверяет его на клоне control, включая browser constraint validation `min`, `max` и `step`; невалидное значение не касается исходного поля. После fill сверяются фактическое value и validity. Primitive не нажимает Save/Submit и классифицируется как WRITE.

Slider primitive поддерживает native `input[type=range]` и `role=slider`. Он читает фактические min/max/current и стандартный native step либо явный `aria-valuestep`/`data-step`, блокирует выход за диапазон, несовпадение шага и более 500 keyboard steps. Значение меняется Arrow-клавишами с учётом orientation и считается установленным только после повторного чтения control. Save/Apply остаётся отдельным действием.

Tree inspector возвращает ограниченный список видимых `treeitem` с именем, level, expanded, selected, checked и disabled. Expand primitive требует единственное точное дерево и item с явным `aria-expanded`, использует стандартные ArrowRight/ArrowLeft и сверяет состояние после события. Раскрытие ветки относится к INTERACT, не выбирает значение и не сохраняет форму.

Tree selection primitive требует явный boolean-контракт `aria-selected` или `aria-checked`, использует Space и повторно читает тот же атрибут. Отсутствующий контракт, disabled item и неоднозначность блокируются до действия. Selection относится к WRITE; раскрытие ветки и последующий Save остаются отдельными действиями.

Popover lifecycle primitives требуют единственную видимую кнопку и единственный элемент, связанный через её `aria-controls`. Открытие проверяет появление popup, read-only inspector возвращает ограниченный снимок содержимого и controls, закрытие отправляет Escape и проверяет исчезновение. Эти действия не нажимают Apply/Save; popup без явной связи блокируется.
Класс открытия определяется тем же v069-классификатором, что и обычный клик по имени trigger: опасная кнопка не становится безопасной только из-за `aria-controls`.

Popover option primitive действует только внутри уже открытого и однозначно связанного popup. Он требует единственную видимую `role=option` с явным boolean `aria-selected`, нажимает её и подтверждает состояние. Без контракта выбора, при disabled или неоднозначности действие блокируется; Apply/Save остаётся отдельным шагом. Обычное значение классифицируется как WRITE, destructive-имя не понижается ниже DESTRUCTIVE.

Popover button primitive нажимает только единственную видимую enabled-кнопку с точным именем внутри уже открытого popup, однозначно связанного с trigger через `aria-controls`. Любая такая кнопка проходит WRITE-policy, destructive-имя — DESTRUCTIVE-policy; это не обход подтверждения обычного клика. Возвращается снимок до/после и факт клика, но не делается вывод об успешной бизнес-мутации: её нужно проверить отдельным наблюдением. Отсутствующая, неоднозначная и disabled-кнопка блокируется до действия.

File input inspector ищет единственное нативное `input[type=file]` по видимой метке, включая скрытое поле с видимым связанным label, и возвращает только `accept`, `multiple` и число файлов. Upload primitive принимает идентификатор встроенного harmless fixture `sample-text`, а не путь или содержимое произвольного файла. Он сверяет `accept`, выбирает fixture через браузер и проверяет имя, MIME и размер выбранного файла. Событие `change` может автоматически отправить файл на сервер, поэтому выбор — WRITE; успешный backend upload требует отдельного evidence. Содержимое файлов пользователя не читается и не возвращается модели.

Upload action дополнительно сопоставляет ответы fetch/XHR текущего действия только с запросами POST/PUT/PATCH, тело которых содержит байты встроенного fixture. Это даёт статусы `accepted_response_observed`, `rejected_response_observed` или `not_observed` без вывода тела запроса. Даже 2xx означает лишь принятый транспортный запрос, а не сохранение ресурса. Флаг `upload_persistence_verified` остаётся false; для подтверждения нужно независимое read-only наблюдение после повторного открытия списка/страницы или предметный API-check.

Download primitive требует единственную видимую enabled-кнопку или ссылку с точным именем, ожидает реальное событие скачивания и не считает один клик успехом. Файл до 10 MiB сохраняется под случайным именем в приватной директории артефактов браузерной сессии. Агенту возвращаются suggested filename, размер, ограниченное определение формата по сигнатуре и SHA-256, но не содержимое. `verified` возможен только при совпадении ожидаемого имени, формата (если задан) и известного ожидаемого SHA-256; без хэша статус `metadata_only`. Кнопка проходит как минимум WRITE-policy, destructive-имя не понижается. Это проверяет полученный файл, но не доказывает источник или корректность бизнес-данных без предметных ожиданий.

Структурная проверка принимает только выданный текущей browser session `download_id`, а не произвольный путь. Для CSV она сравнивает точные ожидаемые заголовки, диапазон числа строк и постоянство числа колонок, не возвращая строки; для PDF через pypdf сравнивает ожидаемое число страниц, не извлекая текст. ID предыдущего test case при сбросе browser context больше не доступен. Это ограниченная проверка структуры, не семантическая валидация содержания документов.

Agent observability primitive работает только с уже открытой точной карточкой КЕ. Он берёт видимый статус рядом с именем КЕ и сопоставляет его с ответами CI, agent и system monitoring, которые текущая browser session получила штатным UI-путём. Из ответов возвращаются только CI/agent ID, ОС, архитектура, версия, статусы, timestamps и ограниченные числовые показатели; ключи и полные payload не копируются в отчёт. Проверяется связь ID и свежесть monitoring sample. `PASS` означает только согласованное наблюдение online и свежей телеметрии, не успешную установку плагина или VNC. Offline, противоречивые и устаревшие данные дают `BLOCKED` с причиной. `last_online_at` показан отдельно и не используется как heartbeat без подтверждённой семантики продукта; `cpu_usage` и `ram_usage` остаются raw до подтверждения единиц измерения.

Keyboard primitive принимает только закрытый список клавиш и chords. Tab, Shift+Tab, Escape и Control+A классифицируются как INTERACT. Enter, Space, стрелки, Home/End/Page, Backspace, Undo/Redo chords, Shift+Enter и Alt+ArrowDown считаются WRITE, потому что способны изменить focused control или отправить форму. Delete считается DESTRUCTIVE. Control-based chord требует точный semantic target; неизвестные сочетания, включая прямые Control+C/X/V, не исполняются. Focus-order primitive фокусирует первый точный semantic target, проходит реальный Tab sequence и возвращает наблюдаемые focused elements и первое расхождение.

Для copy/paste используется отдельный private clipboard внутри памяти текущей browser session. Copy принимает только точный input, textarea или contenteditable, блокирует password/token/secret-like source, ограничивает значение 4096 символами и возвращает только размер и статус — не содержимое. Paste использует только этот private buffer, блокирует sensitive или non-editable target и классифицируется как WRITE. Системный clipboard ОС не читается и не изменяется; private buffer не сохраняется в Job, evidence или artifacts и может быть явно очищен.

Pointer primitives используют только однозначно найденные видимые endpoints. Drag-and-drop требует разные source/target и сохраняет bounding boxes до и после. Для reorder он до мутации снимает порядок верхнеуровневых semantic items в точном container, а после действия сравнивает весь exact order либо заданную subsequence. Несовпадение возвращается как ошибка при честно отмеченной выполненной мутации. Отдельный read-only order inspector позволяет повторить ту же проверку после reload: только этот второй match доказывает сохранение порядка, тогда как результат drag доказывает лишь состояние текущего UI. Resize ограничивает delta диапазоном, поддерживает правую, нижнюю и угловую границы и считается успешным только при фактически изменившемся bounding box. Изменяющие pointer actions относятся к WRITE и блокируются read-only policy.

Table primitives работают с одной однозначно найденной таблицей. Snapshot ограничивает объём и сохраняет headers, aria-sort, cells, values_by_header и row signature. Sort принимает точный header и подтверждает направление через aria-sort; при отсутствии ARIA отдельно сообщает только наблюдаемое изменение порядка. Header matching умеет отделять имя колонки от текста вложенных sort/filter controls, но всё равно требует единственное совпадение. Row selection ищет строку по точной ячейке и единственный checkbox внутри указанной таблицы, не запуская bulk action. Для cross-page workflow runtime строит устойчивый ключ из page scope, имени таблицы и headers; query-параметр страницы в ключ не входит. Pagination считается успешной только если после точного control изменился row signature.

Read-only table inspector допускает безопасный fallback на единственную видимую HTML-таблицу, если модель передала визуальное имя раздела, а сама таблица не имеет caption/ARIA label. Fallback возвращается явно как `unique_visible_fallback`; при двух и более таблицах сохраняется блокировка по неоднозначности. Sort, selection, pagination и другие взаимодействия не используют этот fallback и сохраняют строгий scope.

Inline column filter связывается с точным header по cell index и допускается только при единственном видимом filter control в соответствующей header-cell. Popover filter требует единственную точную trigger-кнопку внутри header, однозначный popup через `aria-controls` либо единственный overlay, единственное value field и точную Apply-кнопку. Operator выбирается только из единственного native select с единственной совпавшей option. Результат сообщает факт отправки фильтра и rows before/after, но не объявляет server filter успешным только по клику.

Read-only pagination inspector отдельно возвращает visible row count, server-side total, видимый диапазон, current page и состояния controls. Total принимается только из явных `aria-rowcount`/`data-total*` attributes либо ограниченных видимых шаблонов `1-20 of 137` / `Всего: 137`; количество DOM-строк не подменяет total. Select-all управляет только header checkbox и проверяет все видимые row checkboxes. Bulk preview является строго read-only: он возвращает enabled/disabled action state и число выбранных строк, но никогда не нажимает кнопку. Любая массовая операция остаётся отдельным вызовом и классифицируется обычной policy по её смысловому имени.

### Compatibility Layer

Compatibility probe является read-only операцией и выполняется после навигации на целевую страницу до первого WRITE. Он определяет доступные стандартные контракты: HTML table, ARIA grid, native select/multiselect, ARIA combobox/listbox, checkbox/radio/switch, slider, tree, dialog, date/file inputs, contenteditable, Shadow DOM и canvas. Дополнительно вычисляется доля видимых интерактивных элементов с semantic name.

Из устойчивых признаков строится version-independent capability contract и SHA-256 fingerprint. Динамические количества строк и значения данных в fingerprint не входят. Page key нормализует числовые и UUID path segments. Snapshot сохраняется в текущем Job и сравнивается с последним snapshot того же стенда и page key. Изменение adapters, feature flags или semantic coverage фиксируется явно; canvas-only UI и низкое semantic-name coverage помечаются как capability gaps. Это позволяет менять browser adapter, не переписывая Planner, policy, Job Store, evidence и cleanup.

В управляемом regression case после первого открытия страницы Core требует успешный capability probe до первого WRITE или DESTRUCTIVE. Если snapshot отсутствует, агент получает единственный обязательный OBSERVE-кандидат `browser_probe_capabilities`; если probe вернул capability gaps, мутация блокируется fail-closed. Совместимый, но изменившийся fingerprint сохраняется как риск и не блокирует сценарий. Guard включён только для основного case execution; Cleanup Manager остаётся в собственном более строгом контуре exact-target и v069 confirmation.

Табличная проверка вынесена в отдельный read-only инструмент: уникальная строка определяется по точному значению одной ячейки, после чего в evidence сохраняются полный текст строки, массив ячеек, заголовки и отображение значений по заголовкам. Проверка не требует и не предполагает ARIA role строки.

Role в read-only semantic inspection является проверяемым сужающим hint. Если live DOM её не подтверждает, runtime сохраняет точное имя, выполняет остальные строгие стратегии и помечает результат как role fallback; неподтверждённая роль не создаёт бесконечный not-found цикл.

Core также хранит в памяти case ключи неуспешных точных semantic inspections. Повтор того же имени не выполняется в браузере второй раз, даже если модель меняет только предполагаемую role: case завершается `BLOCKED` с отдельной машинной причиной. Это ограничение не подменяет FAIL и не создаёт ложного доказательства отсутствия элемента.

Аналогичный guard действует после пользовательского отказа на WRITE или DESTRUCTIVE: идентичная мутация не запрашивается и не выполняется повторно, а case получает отдельную причину BLOCKED. Для `resource_register` Core также проверяет происхождение `external_id`: значение допустимо только когда ранее наблюдалось именно в ID-поле tool result, а не просто совпало с именем ресурса.

Поиск полей сначала использует accessibility role, стандартную связь label, placeholder и HTML metadata. Если UI-библиотека вывела метку отдельным `div` или `span` без `for`/`id` и ARIA, runtime сначала рассматривает ближайший контейнер и принимает его лишь при наличии ровно одного видимого редактируемого элемента. Когда метки и поля находятся в соседних DOM-ветках, последний fallback связывает метку только с ближайшим полем ниже неё при горизонтальном пересечении и явном преимуществе по расстоянию. Несколько равнозначных кандидатов считаются неоднозначностью, а не поводом угадывать.

Изменяющие REST-инструменты удаления и архивирования не входят в обычный набор инструментов агента. Они доступны только Cleanup Manager. Сам обработчик остаётся в trusted runtime и выполняет preflight GET, требует ровно одно точное совпадение, использует безопасный идентификатор и проверяет результат повторным GET. Для DELETE точное совпадение должно исчезнуть; для archive тот же единственный объект должен иметь универсально распознаваемый архивный признак. Уже архивный объект считается выполненным cleanup без повторного POST.

Browser runtime может возвращать подробное состояние страницы, но в LLM-контекст поступает ограниченное рабочее представление. Объёмные повторяющиеся данные строк таблиц, сетевых событий и текстов сокращаются. Приоритет получают действия, которые нужны для следующего шага: открытые menu items, поля формы, кнопки, ссылки и вкладки. Из последовательности состояний только последнее остаётся подробным; старые browser results заменяются короткой историей выполненных действий, URL, статусов и evidence IDs. Полный исходный результат сначала проходит через evidence и observation pipeline, поэтому сжатие контекста не меняет runtime-факты и verdict.

### Job Store

Job Store — постоянное файловое хранилище состояния QA Job. Оно переживает остановку UQA и позволяет продолжить анализ или cleanup позже.

В Job сохраняются:

- исходный запрос и идентичность стенда;
- test cases и checks;
- evidence и observations;
- итоговые статусы и summary;
- test resources и история cleanup.
- persistent выбор строк таблиц по test case и устойчивому ключу таблицы.

Запись выполняется атомарно. Чувствительные поля metadata проходят очистку перед сохранением.

### Persistent Table Selection Ledger

Selection ledger хранит точные строки, которые агент выбрал или снял в рамках одного test case, даже если следующая страница таблицы уже заменила DOM предыдущей. Запись содержит `selection_id`, `case_id`, устойчивый `table_selection_key`, hash полного набора ячеек `table_row_key`, отображаемое имя строки, текущее состояние выбора, page signatures и timestamps. Поэтому одинаковые отображаемые имена на разных страницах не сливаются автоматически.

Ledger является только памятью намерения агента. Он не доказывает, что frontend действительно удерживает checkbox между страницами, не считается runtime evidence для PASS и всегда возвращает `bulk_action_authorized=false`. Массовое Save/Archive/Delete остаётся отдельным действием и проходит обычную v069 policy.

### Persistent Resource Ledger

Ledger хранит каждый тестовый ресурс независимо от памяти модели.

Основные данные ресурса:

- внутренний `resource_id`;
- универсальный `type`;
- точное `name`;
- `external_id`, если он известен;
- создавший его test case;
- текущее состояние;
- необходимость cleanup;
- зависимости от других ресурсов;
- безопасная metadata;
- история cleanup attempts и events.

Основные операции:

- регистрация подтверждённо созданного ресурса;
- получение одного ресурса;
- read-only авторизация одного точного изменения по ownership, disposable-флагу, cleanup-контракту и allowlists поля/значения;
- фильтрация списка ресурсов;
- изменение состояния и metadata;
- выбор кандидатов на cleanup;
- начало, журналирование и завершение cleanup attempt;
- пересчёт общего cleanup status Job.

### Cleanup Manager

Cleanup Manager обрабатывает только ресурсы из ledger. Он не получает право свободно выбирать объект удаления.

Защитные условия:

- один запуск работает с одним точным resource;
- целевой стенд совпадает со стендом Job;
- имя и идентификатор не угадываются;
- исходная навигация может быть повторена только до первой мутации;
- Create/Add/Save из исходного сценария не повторяются;
- REST-cleanup разрешается только по точным аргументам, сформированным Core из metadata и наблюдавшегося endpoint;
- destructive-вызов проходит через v069 policy;
- destructive-клик, открывший одноимённую кнопку подтверждения, считается только
  первым шагом диалога; mutation фиксируется после отдельного подтверждённого клика;
- Browser Runtime после каждого semantic click отдельно считает видимые
  одноимённые кнопки, поэтому confirm-popover определяется независимо от
  сокращённого списка model-facing interactive elements;
- наблюдённую одноимённую confirm-кнопку вызывает сам Core точными аргументами,
  не полагаясь на решение модели; второй клик повторно проходит v069 policy;
- после первого подтверждённого destructive-вызова повторная mutation для того
  же ledger-ресурса запрещена; recovery может выполнять только read-only post-check;
- если исходное evidence фиксирует ресурс как точную строку таблицы, recovery
  повторяет тот же exact table-row inspector до обращения к модели;
- если archive оставляет строку в таблице, Core открывает context menu этой же
  exact-строки и принимает cleanup только после наблюдаемой замены действия
  `Archive` на обратное `Unarchive`;
- `cleaned` допустим только после runtime-проверки отсутствия ресурса; для
  табличных ресурсов Core принимает точный `table_row_not_found`, для остальных
  элементов — точный `semantic_element_not_found`;
- неоднозначность или отсутствие поддерживаемого действия оставляет ресурс `pending`.

Порядок cleanup учитывает зависимости: зависимые и более поздно созданные ресурсы удаляются раньше их родителей.

### Product Blocker Registry

Реестр отделяет ограничение продукта от дефекта агента. Для blocker сохраняются capability, причина, статус, версии компонентов, условие повторной проверки и история изменения состояния.

Статусы:

- `open` — ограничение подтверждено на текущих версиях;
- `needs_recheck` — версия связанного компонента изменилась;
- `resolved` — возможность проверена и blocker закрыт.

Текущий blocker: Access Zone можно создать и изменить, но на проверенных версиях U-Connect нет работающего UI- или backend-маршрута удаления/архивирования. Созданный тестовый ресурс остаётся в ledger как `cleanup_pending`.

Текущий blocker `uc-tasks-server-db-pool-exhausted`: на backend `4.9.0` / tasks-server `4.0.2` сервис исчерпывает SQLAlchemy pool (`size=5`, `overflow=15`) и после 30 секунд возвращает ошибку вместо списка agent tasks. Одновременно у наблюдавшихся Windows/Ubuntu КЕ перестали обновляться monitoring samples и plugin audit. Blocker сохранён в persistent registry с условием повторной проверки после восстановления пула или смены версии; managed WRITE остаётся запрещён до успешного task-list preflight и свежей telemetry.

### Product Knowledge Pipeline

Observations извлекаются из фактических результатов инструментов. На их основе формируются candidate facts. Кандидаты проходят проверку области применимости и конфликтов перед продвижением в подтверждённые знания.

Такой подход позволяет расширять базу знаний по стендам, версиям и функциям продукта без жёсткого кодирования поведения конкретных сущностей в Core.

На момент v150b `knowledge_search` искал индексированные документы через SQLite FTS5, но не извлекал автоматически подтверждённые facts из product knowledge store. После успешного case запускается генерация и ingestion поддерживаемых candidate facts; автоматическая promotion зависит от типа факта и известной architecture/server version. Это не обучение весов модели и не гарантированное накопление знаний каждым PASS. В tab/renderer прогонах v150b поиск документов не вызывался, кандидатов было ноль. Полный цикл «выбрать подходящее подтверждённое знание → использовать как подсказку → перепроверить после смены версии → сохранить подтверждение/конфликт» остаётся отдельным этапом; знание никогда не заменяет текущее runtime evidence.

v150c подключает ограниченное чтение product memory к результату `knowledge_search` в основном action loop. Reader открывает существующую SQLite базу строго `mode=ro`, не запускает migrations/инициализацию. Применяются version/scope индексы существующей схемы: точные installation architecture и server version из identity текущего Job; status=ok, не partial deployment. Неизвестная identity даёт unavailable, не подбор ближайшей версии. Допускаются только verified, без conflict/deprecated markers, с verified_at и confirmation в той же области. Первоначальный adapter поддерживает `ui_api_binding`, выдаёт лишь ограниченные allowlisted поля и source case references, исключает sensitive-like/URL-query значения. До 200 scoped candidates ранжируются по точному пересечению слов запроса, до пяти результатов. Это не embeddings и не семантическая гарантия полного поиска; превышение scan budget явно отмечается.

Memory payload передаётся модели как untrusted hint с `evidence_for_pass=false`; документационный ответ остаётся сохранён. Сам reader не выполняет UI/API-команд, не меняет policy и не продвигает факты. Frontend version отсутствует в исходной scope-схеме и явно не считается проверенной совместимостью. Автоматическая загрузка на каждый case, подтверждение новых tab/telemetry фактов, актуальная identity для prepared Jobs и полный recheck после обновления ещё не реализованы этим этапом. Read-only audit существующей памяти: один `ui_api_binding`, один verified scope, пять confirmations. Обнаруженная текущая identity стенда lab: ansible/server 4.9.0; релевантный запрос возвращает один факт, запрос с другой server version — ноль.

v150c integration probe передал результат read-only retrieval реальной qwen3:14b: модель правильно вернула число фактов 1 и evidence_for_pass=false. Это проверка передачи контекста, не тест продуктовой функции и не обучение модели. Изолированный action-loop test подтверждает, что product_memory включается в knowledge_search response и неизвестная identity не выдаёт никаких фактов. Дополнительно проверены wrong version/architecture, candidate/conflict scopes, sensitive-like поля, отсутствие файла БД и неизменность его хэша при чтении.

v150d добавляет opt-in `memory_query` в requirement подготовленного read-only Job. Перед запуском заново обнаруживается identity сохранённого стенда: version, architecture, partial-deployment и UTC checked_at сохраняются в Job, старый паспорт не используется при сбое обнаружения. Читается только версия-совместимая память, её payload передаётся модели как отдельные недоверенные данные с запретом выполнять remembered fill/action. В case сохраняется `memory_context`: число загруженных фактов, их keys, время identity check, evidence_for_pass=false и binding_reconfirmation=not_performed. Это аудит загрузки контекста, не доказательство, что модель выбрала маршрут именно благодаря памяти.

Opt-in не меняет legacy Jobs без memory_query, не разрешён для write profiles и перед сохранением повторно проверяет pending Job, stand и requirement. При изменении Job во время обнаружения версия/контекст не записываются. Детектор возвращает только allowlisted поля: секреты, произвольные ошибки и raw responses не сохраняются. Сама product memory не изменяется этим этапом. Для существующего Search by name → GET/name факта повторное открытие карточки не подтверждает API-binding: необходим отдельный UI filter action через прежнюю policy и новый закрытый network window. ### v151h: persistent read-only restriction имеет приоритет над preflight

Для managed Job проверка запрета пользователя получает исходный persistent request, а не последнее служебное user-role сообщение Core. Explicit create со scoped запретом менять существующие объекты не становится глобально read-only. Исторические Jobs не переписываются.

## Проверка качества

Перед установкой изменений выполняются:

- резервное копирование изменяемых production-файлов;
- синтаксическая проверка Python-модулей;
- изолированные smoke-tests planner, policy, browser semantics, ledger, cleanup и blockers;

Постоянный smoke-suite должен запускаться одной командой из стабильного каталога и не зависеть от временных файлов.

В работе:

- расширение закрытого fixture allowlist отдельными фиксированными профилями только после отдельной проверки каждого профиля;

Core формирует для каждой managed-фазы явный next-step contract: точное имя tool и уже связанные с Job безопасные аргументы (`stand URL`, exact CI, capability probe, fixture ID, затем private task ID). Контракт добавляется до первого вызова модели, после каждого успешного одиночного tool-call, при преждевременном финальном ответе и вместе с блокировкой неверной попытки. После фазы `verify` Core переходит в `verdict` и не восстанавливает устаревший generic navigation-preflight из истории сообщений. Это не обходит action-policy: вызов `create` остаётся `WRITE`, а cleanup — отдельным `DESTRUCTIVE` действием; изменение лишь убирает лишний поиск меню и случайные вызовы generic controls.

Planner отделяет критерии продукта от служебного формата ответа агента. Формулировки вроде «вернуть verdict»/«verdict возвращён» удаляются из `planned_checks`: verdict формируется после проверки evidence и не может требовать отдельного evidence сам для себя. Реальные продуктовые assertions — например, создание задачи, закрытый результат и `error code = 0` — сохраняются без изменений.

Атомарный roundtrip проверяет заданную последовательность `Next`, полный возврат `Back`, закрытие и отсутствие изменяющих запросов; submit-like кнопки в этом режиме запрещены. Отдельные `Save/Submit/Delete` сохраняют обычную v069-классификацию.
- Кастомные ARIA calendar overlays: exact trigger через `aria-controls`, обязательный `role=grid`, read-only snapshot наблюдаемых дат и policy-controlled выбор одной точной date option с post-click verification.
- Custom time-picker overlays: exact trigger через `aria-controls`, обязательный `role=listbox`, read-only snapshot наблюдаемых значений времени и policy-controlled выбор одной exact time option. Нестандартные date/time widgets без ARIA-контракта блокируются fail-closed.
- Upload/download: безопасный fixture upload; download проверяет имя, сигнатуру и hash, а структурный inspector — CSV headers/row bounds, PDF page count, JSON top-level type/required keys/item bounds и точные размеры PNG/JPEG. Содержимое файлов не возвращается модели.
- Modal/dialog и toast/notification через фактические accessibility roles `dialog`, `alertdialog`, `alert`, `status`.
- Responsive-проверки через фиксированные профили `mobile` (390×844), `tablet` (768×1024) и `desktop` (1440×900): Core получает screenshot, точные размеры документа и машинный флаг horizontal overflow без произвольных размеров viewport.
- Базовый accessibility audit страницы: машинно выявляет видимые интерактивные элементы без accessible name, изображения без `alt`, duplicate `id` и broken ARIA references; результат содержит общий `accessibility_passed` и конкретные категории нарушений.
- Semantic inspector дополнительно измеряет фактическую геометрию элемента: координаты и размер, пересечение с viewport, долю видимой после clipping области, минимальный touch target и перекрытие центра другим элементом. Это отличает присутствующий в DOM элемент от реально доступного пользователю без выполнения клика.
- Для проверки визуальных состояний тот же inspector возвращает машинные флаги `focus/focus-visible/hover/checked/invalid` и ограниченный безопасный набор computed CSS: display/visibility/opacity, pointer-events/cursor, цвета, border/outline, шрифт и text decoration. Произвольное чтение CSS или выполнение JavaScript модели не разрешено.
- Каждое browser evidence содержит frontend health: console errors, необработанные JavaScript exceptions, HTTP errors и failed requests, а также общий `frontend_health_passed`. URL сетевых сбоев проходит ту же очистку query-параметров с секретами; stack trace и response body автоматически не раскрываются.
- Для ссылок, штатно открывающих новую вкладку, отдельный semantic workflow требует единственную точную видимую ссылку с `target=_blank`, HTTP(S) и заранее заданный URL prefix того же origin. Core проверяет URL/title/text preview, закрывает только дочернюю вкладку и доказывает восстановление исходного browser context; небезопасные схемы и неожиданный origin блокируются до клика.
- История браузера проверяется отдельным одношаговым workflow `Back/Forward`: Core разрешает только same-origin HTTP(S), требует ожидаемый URL prefix и возвращает фактический URL/status. Сохранение фильтра, формы или выбранной вкладки после возврата доказывается обычным semantic inspector, а не предполагается из самого факта навигации.
- Встроенный iframe наблюдается по единственному точному `title`, `aria-label` или `name` и ожидаемому HTTP(S) URL prefix. Inspector сверяет origin, URL, title, ограниченный text preview и число интерактивных элементов внутри, не переключая top-level context; наличие frame само по себе не считается доказательством работающего VNC или другого интерактивного приложения.
- Для VNC, remote console и media preview iframe inspector отдельно считает canvas/video, возвращает внутренние и отображаемые размеры, visibility, video ready state и общий `surface_ready`. Этот флаг доказывает наличие готовой поверхности ненулевого размера, но ещё не доказывает изменение кадров или возможность управлять удалённой системой.
- Изменение VNC/video кадра проверяется двумя приватными screenshot одного exact iframe через ограниченный интервал и сравнением SHA-256. Модель получает только hashes, boolean `surface_changed` и соответствие ожидаемому изменению; pixels не возвращаются. Изменившийся кадр не считается доказательством успешного ввода или результата команды.
- Атомарная read-only проверка VNC/remote-console объединяет identity/origin, готовность поверхности и ожидаемую активность кадра в один Core-owned verdict. Она не отправляет pointer или keyboard input и не может выдать `PASS`, если iframe отсутствует, неоднозначен, ушёл на другой origin, имеет нулевую поверхность либо не соответствует ожидаемой смене кадра.
- Координатный клик по VNC/canvas разрешён только внутри заранее подтверждённого exact iframe с `surface_ready=true`, задаётся нормализованными координатами и всегда классифицируется как `WRITE`. До клика действует v069 confirmation, после — private before/after screenshot hashes; изменение кадра подтверждает реакцию поверхности, но бизнес-результат проверяется отдельным evidence.
- Клавиатурный ввод в VNC ограничен служебными клавишами (`Tab`, `Enter`, `Escape`, arrows, navigation и несколько безопасных chord) без произвольного текста. Инструмент сначала фокусирует точку surface, отдельно учитывает ожидаемое изменение от focus click, затем проверяет реакцию на key по private hashes; всё действие классифицируется как `WRITE`.
- Hover-only подсказки проверяются через единственный точный semantic target и конкретный `role=tooltip`: Core требует, чтобы tooltip отсутствовал до наведения, появился с ожидаемым accessible name/text и исчез после ухода курсора. Простое изменение CSS `:hover` без наблюдаемого tooltip не считается PASS.
- Native browser dialogs (`alert/confirm/prompt/beforeunload`) обрабатываются одноразовым handler с точным ожидаемым type/message. Любое несовпадение fail-closed вызывает `dismiss`; `accept` классифицируется как `WRITE`, а destructive trigger сохраняет `DESTRUCTIVE`. Prompt text в evidence не возвращается.
- Native constraint validation формы проверяется без Submit: Core возвращает только идентичность invalid control и причины `required/type/pattern/range/step/length/bad input/custom validity`, не раскрывая введённые values. Audit может быть ограничен точной формой по `aria-label/name/id`.
- Асинхронное состояние загрузки проверяется read-only инструментом в точном scope по `aria-label/name/id`. Core наблюдает фактические `aria-busy=true` и `role=progressbar`, умеет подтвердить текущее `busy/ready` и при необходимости требует доказанный переход `busy → ready` за ограниченное время. Отсутствие индикатора без ранее наблюдённого busy не считается доказательством lifecycle, если включён `require_transition`.
- Кратковременные уведомления проверяются отдельным read-only lifecycle по точному тексту и фактическому `role=alert/status`. Core может дождаться появления одного уведомления либо доказать последовательность `visible → dismissed`; неоднозначные совпадения блокируются, а отсутствие уведомления без ранее наблюдённого `visible` не считается доказательством исчезновения при `require_seen=true`.
- ARIA-ошибки полей проверяются без Submit и без возврата values: `aria-invalid`, связанные `aria-errormessage/aria-describedby`, отображаемый текст ошибки и broken references.
- Состояние точного semantic control можно ждать read-only до `visible/hidden/enabled/disabled/checked/unchecked`; неоднозначный target блокируется, а `require_seen` требует наблюдённый переход.
- Dirty-state формы определяется сравнением приватных SHA-256 fingerprints. Значения полей не попадают в evidence или модель; Core сообщает только наличие baseline, число controls и `dirty/clean`.
- ARIA tabs проверяются как единый контракт: один видимый tablist, ровно один `aria-selected=true`, существующие `aria-controls` и видимая panel выбранной вкладки.
- Disclosure/accordion проверяется по согласованности `aria-expanded`, `aria-controls` и фактической видимости controlled panel.
- Modal focus trap проверяется ограниченным циклом Tab внутри exact dialog. Инструмент меняет только клавиатурный фокус, фиксирует выход за границы dialog и классифицируется как `INTERACT`, а не WRITE.
- Видимая heading hierarchy проверяется по native `h1–h6` и `role=heading`: уровни, пустые имена, пропуски уровней и число `h1`.
- Структура landmarks проверяется для `main/navigation/banner/contentinfo/complementary/region`: один main, singleton landmarks и уникальные labels повторяющихся областей.
- Ссылки проверяются read-only на accessible name, допустимую URL scheme и защитный `rel` при `target=_blank`; query-параметры с секретами очищаются до evidence.
- ARIA combobox проверяется как связанный контракт `expanded → controls → popup role/visibility → active descendant`.
- Listbox audit проверяет именованные options, selected count и допустимость множественного выбора.
- Menu audit проверяет роли и accessible names menuitems, disabled-state и наличие popup metadata без выполнения пунктов меню.
- Numeric ARIA widgets `progressbar`, `meter` и `spinbutton` проверяются read-only: accessible name, конечные min/max/now, порядок диапазона, попадание значения в границы и допустимый indeterminate progressbar.
- Визуальный read-only audit проверяет WCAG contrast видимого текста на solid backgrounds, фактическое clipping по scroll/client geometry и минимальный размер интерактивных controls. Неподдерживаемые gradient/image backgrounds учитываются отдельно, а не получают ложный PASS.
- Live regions проверяются по допустимым `aria-live` и implicit live roles; dialogs — по accessible name и целостности `aria-labelledby`; form fields — по label и `aria-describedby` без чтения values.
- Document metadata audit проверяет непустой title, валидный `html lang` и единственный responsive viewport. Keyboard shortcut audit обнаруживает безымянные/дублирующиеся `accesskey` и `aria-keyshortcuts`. Autofill audit проверяет autocomplete purpose, особенно `current-password/new-password`, не раскрывая values.
- Frontend security audits read-only проверяют form action/method без values, mixed-content и integrity внешних scripts, а также broken/mixed/autoplay media resources. Все URL проходят очистку секретных query-параметров.
- Performance/accessibility audits проверяют lazy-loading и stable dimensions offscreen media, готовность web fonts через CSS Font Loading API и наличие `prefers-reduced-motion` при длительных CSS animations/transitions.
- Native web-platform contracts read-only проверяют `details/summary`, HTML Popover API (`popover`/`popovertarget`) и `<dialog>` accessible name с согласованностью `open` и фактической видимости.
- Form structure audits проверяют direct `legend` у fieldset, identity/labels/checked-count radio groups и explicit button types внутри form, чтобы обнаруживать случайный implicit submit.
- Access Zone blocker оставить до появления продуктовой поддержки и автоматически перепроверить после изменения версии.

Уже наблюдённый marker допускает FAIL даже при неполном scan, но отсутствие marker при неполном scan даёт BLOCKED, не PASS.

Первоначальные renderer PASS Jobs `20261013-104420-42757c60` и `20261013-112729-8d0dc0b6` не считаются подтверждением отсутствия storage ошибки: screenshot первого показывает сообщение, а дополнительная проверка установила четыре iframe внутри Monitoring panel и marker в одном из них. Первоначальный детектор читал только оболочку. Исторические Jobs сохраняются без переписывания результатов; это известный дефект проверки UQA, исправленный добавлением scoped frame scan, а не устранение продуктовой ошибки.

Для подготовленного tab-контракта Core передаёт модели locked composite route до действий и после открытия страницы. Старые telemetry/plugin подсказки по словам запроса для этого контракта не добавляются. Модель продолжает выбирать вызов инструмента, который проходит прежнюю action policy; STEP/AUTO и защиту от циклов это не изменяет.

`known_renderer_errors_absent` — отдельный per-check контракт. Навигационные проверки могут пройти при ошибке содержимого; renderer check на тех же доказательствах вычисляет FAIL и сохраняет категории по tab. Пустой график/no-data сам по себе не является техническим error marker. PASS означает только отсутствие перечисленных видимых DOM-text markers в проверенном scope и моменте наблюдения, не корректность всех графиков, отсутствие canvas-only/любых ошибок или свежесть данных. Case read_only; Refresh, запуск audit/plugin/task и перезапуск агента не используются.

`prepared_observation_contract` допускает только OBSERVE tools и один явно перечисленный универсальный INTERACT tabs-workflow; произвольные click/write tools в эту схему не входят, их v069 классификация не меняется. Сами вкладки выбираются штатным смысловым инструментом и проверяются по ARIA selected/controls/panel facts. `_tab_details_identity_snapshot` дополнительно сверяет видимый exact details anchor либо ранее подтверждённое повторное имя в деталях после каждого tab click. Исчезновение этого identity или переход на другой origin не принимаются за PASS. `tab_fact` связывает весь запрошенный список с измеренными tab records, не допуская PASS по одному tab вместо всех. Screenshot review не считается автоматическим тестом графиков.

### Зависимости и отложенные направления

### Работа группами этапов

По согласованию с пользователем разработка идёт последовательными группами без запроса подтверждения на каждый патч. Порядок одной группы: проверка исходного состояния, резервные копии, минимальные изменения, профильные проверки, общий runner при изменении Core, реальные разрешённые проверки, обновление документа и Git. Это не отменяет action-policy тестового стенда и не разрешает произвольные изменения инфраструктуры. Нужда в новых доступах либо критическом изменении вне согласованного объёма требует остановки и обращения к пользователю.

1. **Целостность evidence (v147b).** Для всех обычных observation types проверять существование IDs и их связь с evidence того же case. Проверять также IDs внутри assertions. Отсутствующая ссылка при наличии связанных observations блокирует verdict. Специализированные agent summaries продолжают использовать уже реализованную Core-канонизацию, а не доверять модельным IDs. Критерий завершения: положительные и отрицательные smoke для PASS и FAIL; сохранённый пример с вымышленными IDs не оставляет отдельные checks passed. Семантическая достаточность evidence — отдельная следующая группа.
2. **Машинные контракты frontend-навигации.** Сохранять в observations фактическую уникальность строки и identity карточки, закрепить ожидания для каждого planned check и вычислять actual/satisfied внутри Core. Saved-stand origin проверять сравнением origin, а не флагом url_changed. Завершение: положительные и отрицательные fixture проверки плюс новый реальный Job; недостающие признаки дают BLOCKED, подтверждённое противоречие — FAIL.
3. **Реальные read-only agent workflows.** Прогнать подготовленные Jobs телеметрии и плагинов, отделить доступность КЕ от свежести samples/audit и сохранить доказательства по каждому критерию. Не объявлять предыдущие online-статусы текущими. Новые патчи только по воспроизведённым пробелам.
4. **Формы, таблицы и контролируемые изменения.** Уточнить candidate по реальному UI, затем использовать только owned fixtures, allowlists и существующую policy. Проверить ledger и cleanup после штатного завершения и прерывания; не удалять демонстрационные Jobs.
5. **Ограниченный пилот.** Повторяемые сценарии, отрицательные проверки, понятный отчёт о покрытии, демонстрация руководству с открытым списком ограничений. Full-back, новые функции, общая knowledge base и Jira идут после принятия ручного frontend-контура.

В v147b прежняя проверка provenance, ограниченная ui_element, расширена на остальные типы. Read-only повторная валидация Job `20261013-075915-a0e0aff9` вернула три BLOCKED; исходный runtime Job не переписывался. Фактически сохранённые observations пока не содержат row_match_count и details identity; это зафиксированный вход для группы 2, а не повод объявлять сценарий PASS. Резервные копии находятся в `state/backups/v147b`.

Группа 1: базовая правка прошла полный runner `169/169`. После расширения проверки на IDs внутри assertions повторно прошли py_compile, профильный provenance smoke и agent-check-binding smoke. Обе разновидности verdict (PASS и FAIL), вымышленные ID, подмена другим evidence того же case, отсутствие ссылки и вложенные assertion IDs проверены без реальных destructive действий. Действующая проверка provenance не доказывает семантическую достаточность assertions: группа 2 остаётся обязательной.

### v148a — машинные контракты отдельных frontend checks

В requirement подготовленного Job можно сохранить `check_contracts`, привязанные к авторитетным planned check IDs. Core проверяет эти контракты отдельно, вместо использования одной общей UI-проверки для всех критериев. Контракты находятся в данных сценария; модуль вычисления не содержит ветвлений по U-Connect, названию КЕ или версии продукта. Начальный безопасный набор поддерживает exact row count, факт открытия/identity карточки и HTTP(S) origin. Новые виды контрактов требуют явного расширения allowlist и тестов; произвольные выражения не выполняются.

Row inspector сохраняет имя инструмента и row_match_count в ui_element, а открытие exact row details создаёт ui_details_identity с subject, фактами открытия/identity и URL. Core выбирает последнее наблюдение нужного инструмента внутри текущего case, требует точный subject, единственную связь с пригодным evidence и exact=true для строки. Более новое неполное, ошибочное или чужое наблюдение не позволяет вернуться к старому PASS.

Для контрактных checks Core самостоятельно восстанавливает evidence/observation references из доверенных записей — аналогично существующим agent summaries. Модельные ссылки, expected и assertions не являются источником фактов. Core записывает вычисленные actual/satisfied и итог: отсутствие или некорректный тип факта даёт BLOCKED, подтверждённое несоответствие — FAIL, совпадение — PASS. Для origin сравниваются схема, hostname и эффективный порт: переход на новый path допустим, другой порт/origin — нет. Флаг url_changed для этого не используется.

uc-front-001 первым получил три контракта в manifest. При материализации они копируются в requirement; изменение контракта не переиспользует старый Job. Старые Jobs не мигрируются и не переписываются. Другие сценарии пока не получили такие контракты автоматически и не считаются покрытыми этой правкой.

Перед установкой сделаны копии в state/backups/v148a. Профильный smoke проверяет Core integration, замену вымышленных модельных ссылок фактическими, PASS/FAIL/BLOCKED, duplicate row count, exact=false, bool вместо count, чужой subject, false identity, другой host/port, malformed URL, непригодное и неправильно связанное evidence и отсутствие fallback к прежнему успешному наблюдению. Реальных destructive действий нет; STEP/AUTO и action-policy сохраняются.

Реальный read-only Job `20261013-082950-6fca68fa` завершился PASS: все три planned checks passed, у assertions вычислены actual/satisfied (`true`), сохранены четыре evidence и четыре observations. Это доказательство данного exact-row navigation workflow на текущем стенде, не обещание работы любых функций. Группа 2 для начального сценария закрыта; устойчивость требует повторных прогонов. ### Независимые agent-факты и Core-owned результат — v148c/v149a

**Наблюдения.** Summarizers сохраняют наблюдённый agent ID, monitoring CI ID и audit agent ID отдельно от ожидаемой связи CI→agent. Observation extractor сохраняет их вместе с конкретным observer, текущим browser URL и идентификаторами захваченных ответов. Чужой host/scheme/port относительно сохранённого стенда не принимается за доказательство, даже при совпадении имени КЕ.

**Контракты.** `agent_fact` сверяет фактические ID и необходимые GET sources. Для monitoring checks дополнительно требуется связь sample→CI, для plugin checks — связь audit→agent. Наличие одного точного плагина проверяется отдельно от наличия версии. Отсутствие плагина в успешно прочитанном аудите означает FAIL требования наличия; неоднозначность или отсутствующая версия блокируют соответствующую проверку. `validate_reported_fact` проверяет типы статусов, timezone-aware timestamp и конечный числовой возраст с прежней clock-skew tolerance. Offline или расхождение статусов может пройти критерий «статусы сообщены», но не доказывает online/согласованность. Старый timestamp может пройти reporting; freshness=true на старом sample не проходит.

**Завершение.** `prepared_contract_check_templates` работает только для готового regression/read-only сценария с полностью покрытыми planned checks и единственным заранее заданным observer. Неполное покрытие, другой observer или изменяющий профиль отклоняются. После попытки observer Core создаёт исходно BLOCKED checks и пропускает их через обычные coverage/evidence/lifecycle проверки, не обращаясь к модели за итоговым JSON. Ошибка инструмента, отсутствующее наблюдение и непригодное evidence не становятся PASS. Модель продолжает выполнять навигацию; STEP/AUTO и action-policy не меняются.

**Отчёт.** `render_contract_check_summary` публикует вычисленные факты, а не непроверенный текст модели. Timestamp, age и freshness включены в actual каждого agent check и не теряются при существующей текстовой нормализации actual в Job Store; типизированные исходные значения остаются в observations. PASS таких сценариев — подтверждение перечисленных reporting-критериев, не автоматическое доказательство свежести, load status, производительности или здоровья агента.

**Проверки безопасности.** Новые технические smoke используют только fixtures/mocks: неправильные CI/agent/sample/audit IDs, другой origin, отсутствующие GET sources, неоднозначный плагин, отсутствующая версия, malformed/naive timestamp, NaN/Infinity и непригодное evidence. Проверяется сохранение freshness=false и отсутствие второго LLM-вызова для форматирования после observer. Реальные прогоны остаются read-only; runtime Jobs, секреты и резервные копии не входят в Git.
