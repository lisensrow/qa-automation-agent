# Архитектура QA-агента UQA

Статус документа: живое описание текущей архитектуры. Обновляется вместе с изменениями UQA.

## Что умеет агент

- Понимает QA-запрос на естественном языке и превращает его в проверяемый план.
- Отличает одиночный последовательный сценарий от набора независимых test case.
- Выполняет UI-проверки в браузере по смысловым названиям элементов, а не по хрупким координатам.
- Выбирает значения native select и ARIA combobox по точным видимым именам без ручного угадывания option.
- Идемпотентно устанавливает checkbox/switch в требуемое состояние и не переключает уже правильное значение.
- Связывает видимую метку формы с единственным соседним полем даже в интерфейсах с неполной accessibility-разметкой.
- Умеет проверять ожидаемый результат и выносить итог `PASS`, `FAIL` или `BLOCKED` по фактическим данным.
- Не считает клик или отправку формы доказательством успеха: требуется последующая runtime-проверка результата.
- Собирает evidence и observations по каждому test case и хранит их вместе с QA Job.
- Разделяет безопасное наблюдение, обычное взаимодействие, запись и разрушительные действия.
- Сохраняет действующую policy v069: чтение и безопасная навигация выполняются автоматически, изменения и destructive-действия проходят через policy.
- Поддерживает режимы STEP и AUTO без изменения их базовой архитектуры.
- Запоминает созданные тестовые ресурсы на диске в persistent resource ledger, поэтому cleanup можно продолжить после сбоя процесса или модели.
- Выполняет cleanup только для точного ресурса из ledger и проверяет результат по семантике операции: исчезновение после DELETE или подтверждённое архивное состояние после archive.
- Умеет восстанавливать безопасный путь навигации до ресурса по наблюдениям, не повторяя исходные Create/Add/Save-действия.
- Восстанавливает стартовый URL cleanup из подтверждённого browser observation, когда стенд не был записан в текст Job.
- Не разрешает generic Add/Create только на основании любого перехода: открытая страница должна семантически соответствовать целевому типу ресурса.
- Не принимает документированный API endpoint за UI-маршрут: первый не подтверждённый deep link открывается с корня стенда и продолжается через фактически видимую навигацию.
- Поддерживает универсальный UI-cleanup и metadata-driven REST-cleanup без привязки Resource Manager к типам сущностей U-Connect.
- Учитывает зависимости ресурсов и очищает дочерние объекты раньше родительских.
- Регистрирует продуктовые blocker отдельно от ошибок агента и сохраняет версии компонентов, на которых blocker подтверждён.
- Автоматически сверяет версии backend/frontend выбранного стенда с версиями открытых blockers и переводит blocker в состояние повторной проверки при изменении версии.
- Не отправляет SSH-пароли и сохранённые учётные данные модели; работа с ними отделена от LLM-контекста.
- Формирует и накапливает продуктовые наблюдения и candidate facts для дальнейшего расширения базы знаний.
- Архитектура базы знаний допускает масштабирование через нормализованные наблюдения, кандидаты, проверку конфликтов и продвижение подтверждённых знаний, а не через бесконтрольное накопление текста диалогов.
- Ограничивает объём browser state, передаваемый модели, сохраняя приоритет для menu items, полей ввода, кнопок и навигации; исходный result остаётся доступен evidence/observation pipeline.

## Назначение и границы

UQA — универсальный QA-агент для выполнения регрессионных и диагностических сценариев на выбранном тестовом стенде. Ядро управляет планом, policy, доказательствами и состоянием задания. Модель выбирает следующий осмысленный шаг только внутри набора инструментов и ограничений, которые передало ядро.

Resource Manager не содержит ветвлений по конкретным сущностям U-Connect. Для него пользователь, зона, политика или запись — это тестовый ресурс с типом, именем, внешним идентификатором, состоянием, зависимостями и metadata.

## Основной поток выполнения

1. UQA принимает запрос и определяет целевой стенд.
2. Planner создаёт один или несколько test case. Последовательный workflow остаётся одним case с несколькими checks.
3. Для каждого case агент выполняет наблюдения и действия через разрешённые инструменты.
4. Core классифицирует каждое действие и применяет policy до исполнения.
5. После каждого значимого шага сохраняются evidence и observations.
6. Созданный тестовый объект немедленно регистрируется в resource ledger.
7. Verdict строится по фактическим checks: `PASS`, `FAIL` или `BLOCKED`.
8. Cleanup Manager получает pending-ресурсы, очищает их в безопасном порядке и сохраняет каждую попытку.
9. Подтверждённая невозможность cleanup на стороне продукта регистрируется как product blocker.

## Компоненты

### UQA Core

Главный координатор. Хранит диалоговый контекст, запускает planner и test cases, выдаёт модели инструменты, применяет action-policy, записывает результаты и запускает cleanup.

Ключевые обязанности:

- выбор и фиксация стенда;
- отделение credentials от модельного контекста;
- управление STEP/AUTO;
- классификация действий;
- исполнение tool call через policy;
- проверка полноты и качества verdict;
- координация ledger и Cleanup Manager;
- показ статуса и открытых product blockers.

Navigation Resolver использует задачу, локальную документацию и только фактически видимые navigation labels. Для иерархических меню он выбирает ближайшую смысловую категорию, затем переоценивает вновь открывшиеся пункты. Если открытая страница не соответствует целевому понятию, Core продолжает требовать навигацию и не передаёт generic Add/Create в mutation policy.

Первое открытие браузера в managed case имеет отдельную защиту: глубокий URL разрешается без нормализации только когда пользователь указал его дословно. Иначе Core открывает origin того же стенда. Это не даёт модели превратить найденный API endpoint или придуманный `/app/...` в непроверенный UI-маршрут.

### Planner

Преобразует пользовательскую задачу в исполнимые test cases и checks. Планировщик должен сохранять причинно связанную последовательность действий внутри одного case. Несколько независимых целей могут быть разделены на разные cases.

Если пользователь явно задаёт «один последовательный test case» или эквивалентную формулировку, Core нормализует даже ошибочно разделённый LLM-план обратно в один case, перенося этапы в checks.

Planned checks связываются по Core-owned `planned-*` ID. Если модель сохранила точные уникальные заголовки, но заменила только IDs своими `check-*`, Core может восстановить соответствие один к одному по нормализованному точному title. Неоднозначные, неполные и приблизительные совпадения по-прежнему блокируются.

### Action Policy v069

Policy — обязательный шлюз между намерением агента и фактическим действием.

Классы действий:

- `OBSERVE` — чтение состояния без изменения;
- `INTERACT` — безопасная навигация и раскрытие интерфейса;
- `WRITE` — создание или изменение данных;
- `DESTRUCTIVE` — удаление, архивирование и иные разрушительные изменения;
- `UNKNOWN` — действие, которое нельзя безопасно классифицировать.

Глобальный read-only detector не должен блокировать явно запрошенный managed workflow только потому, что рядом присутствует ограничение «не изменять существующие объекты».

### Browser Tools

Браузерный слой открывает страницы, возвращает состояние интерфейса и сети, находит элементы по семантике, заполняет поля, выбирает варианты в dropdown/combobox, устанавливает checkbox/switch и выполняет клики. Для табличных ресурсов поддерживается выбор точной строки и её context menu.

Операции выбора и установки состояния относятся к WRITE и проходят через тот же action-policy v069, что и заполнение обычных полей; read-only задачи блокируют их до исполнения. Native `select` изменяется только при единственном совпадении видимой option. ARIA combobox раскрывается и принимает только единственную видимую option. Уже выбранное значение native select и уже установленный checkbox/switch сохраняются как `already_satisfied` без повторной мутации.

Обязательные field/value constraints теперь направляют модель одним атомарным вызовом `browser_select_semantic`. Успешный вызов регистрирует выполненную пару field/value в Core, поэтому последующий Save не заставляет агента повторно раскрывать поле и вручную угадывать role option.

Табличная проверка вынесена в отдельный read-only инструмент: уникальная строка определяется по точному значению одной ячейки, после чего в evidence сохраняются полный текст строки, массив ячеек, заголовки и отображение значений по заголовкам. Проверка не требует и не предполагает ARIA role строки.

Role в read-only semantic inspection является проверяемым сужающим hint. Если live DOM её не подтверждает, runtime сохраняет точное имя, выполняет остальные строгие стратегии и помечает результат как role fallback; неподтверждённая роль не создаёт бесконечный not-found цикл.

Core также хранит в памяти case ключи неуспешных точных semantic inspections. Повтор того же имени не выполняется в браузере второй раз, даже если модель меняет только предполагаемую role: case завершается `BLOCKED` с отдельной машинной причиной. Это ограничение не подменяет FAIL и не создаёт ложного доказательства отсутствия элемента.

Аналогичный guard действует после пользовательского отказа на WRITE или DESTRUCTIVE: идентичная мутация не запрашивается и не выполняется повторно, а case получает отдельную причину BLOCKED. Для `resource_register` Core также проверяет происхождение `external_id`: значение допустимо только когда ранее наблюдалось именно в ID-поле tool result, а не просто совпало с именем ресурса.

Поиск полей сначала использует accessibility role, стандартную связь label, placeholder и HTML metadata. Если UI-библиотека вывела метку отдельным `div` или `span` без `for`/`id` и ARIA, runtime сначала рассматривает ближайший контейнер и принимает его лишь при наличии ровно одного видимого редактируемого элемента. Когда метки и поля находятся в соседних DOM-ветках, последний fallback связывает метку только с ближайшим полем ниже неё при горизонтальном пересечении и явном преимуществе по расстоянию. Несколько равнозначных кандидатов считаются неоднозначностью, а не поводом угадывать.

Изменяющие REST-инструменты удаления и архивирования не входят в обычный набор инструментов агента. Они доступны только Cleanup Manager. Сам обработчик остаётся в trusted runtime и выполняет preflight GET, требует ровно одно точное совпадение, использует безопасный идентификатор и проверяет результат повторным GET. Для DELETE точное совпадение должно исчезнуть; для archive тот же единственный объект должен иметь универсально распознаваемый архивный признак. Уже архивный объект считается выполненным cleanup без повторного POST.

Browser runtime может возвращать подробное состояние страницы, но в LLM-контекст поступает ограниченное рабочее представление. Объёмные повторяющиеся данные строк таблиц, сетевых событий и текстов сокращаются. Приоритет получают действия, которые нужны для следующего шага: открытые menu items, поля формы, кнопки, ссылки и вкладки. Из последовательности состояний только последнее остаётся подробным; старые browser results заменяются короткой историей выполненных действий, URL, статусов и evidence IDs. Полный исходный результат сначала проходит через evidence и observation pipeline, поэтому сжатие контекста не меняет runtime-факты и verdict.

### Job Store

Job Store — постоянное файловое хранилище состояния QA Job. Оно переживает остановку UQA и позволяет продолжить анализ или cleanup позже.

В Job сохраняются:

- исходный запрос и идентичность стенда;
- test cases и checks;
- evidence и observations;
- итоговые статусы и summary;
- test resources и история cleanup.

Запись выполняется атомарно. Чувствительные поля metadata проходят очистку перед сохранением.

### Persistent Resource Ledger

Ledger хранит каждый тестовый ресурс независимо от памяти модели.

Основные данные ресурса:

- внутренний `resource_id`;
- универсальный `type`;
- точное `name`;
- `external_id`, если он известен;
- создавший его test case;
- текущее состояние;
- необходимость cleanup;
- зависимости от других ресурсов;
- безопасная metadata;
- история cleanup attempts и events.

Основные операции:

- регистрация подтверждённо созданного ресурса;
- получение одного ресурса;
- фильтрация списка ресурсов;
- изменение состояния и metadata;
- выбор кандидатов на cleanup;
- начало, журналирование и завершение cleanup attempt;
- пересчёт общего cleanup status Job.

### Cleanup Manager

Cleanup Manager обрабатывает только ресурсы из ledger. Он не получает право свободно выбирать объект удаления.

Защитные условия:

- один запуск работает с одним точным resource;
- целевой стенд совпадает со стендом Job;
- имя и идентификатор не угадываются;
- исходная навигация может быть повторена только до первой мутации;
- Create/Add/Save из исходного сценария не повторяются;
- REST-cleanup разрешается только по точным аргументам, сформированным Core из metadata и наблюдавшегося endpoint;
- destructive-вызов проходит через v069 policy;
- destructive-клик, открывший одноимённую кнопку подтверждения, считается только
  первым шагом диалога; mutation фиксируется после отдельного подтверждённого клика;
- Browser Runtime после каждого semantic click отдельно считает видимые
  одноимённые кнопки, поэтому confirm-popover определяется независимо от
  сокращённого списка model-facing interactive elements;
- наблюдённую одноимённую confirm-кнопку вызывает сам Core точными аргументами,
  не полагаясь на решение модели; второй клик повторно проходит v069 policy;
- после первого подтверждённого destructive-вызова повторная mutation для того
  же ledger-ресурса запрещена; recovery может выполнять только read-only post-check;
- если исходное evidence фиксирует ресурс как точную строку таблицы, recovery
  повторяет тот же exact table-row inspector до обращения к модели;
- если archive оставляет строку в таблице, Core открывает context menu этой же
  exact-строки и принимает cleanup только после наблюдаемой замены действия
  `Archive` на обратное `Unarchive`;
- `cleaned` допустим только после runtime-проверки отсутствия ресурса; для
  табличных ресурсов Core принимает точный `table_row_not_found`, для остальных
  элементов — точный `semantic_element_not_found`;
- неоднозначность или отсутствие поддерживаемого действия оставляет ресурс `pending`.

Порядок cleanup учитывает зависимости: зависимые и более поздно созданные ресурсы удаляются раньше их родителей.

### Product Blocker Registry

Реестр отделяет ограничение продукта от дефекта агента. Для blocker сохраняются capability, причина, статус, версии компонентов, условие повторной проверки и история изменения состояния.

Статусы:

- `open` — ограничение подтверждено на текущих версиях;
- `needs_recheck` — версия связанного компонента изменилась;
- `resolved` — возможность проверена и blocker закрыт.

Текущий blocker: Access Zone можно создать и изменить, но на проверенных версиях U-Connect нет работающего UI- или backend-маршрута удаления/архивирования. Созданный тестовый ресурс остаётся в ledger как `cleanup_pending`.

### Product Knowledge Pipeline

Observations извлекаются из фактических результатов инструментов. На их основе формируются candidate facts. Кандидаты проходят проверку области применимости и конфликтов перед продвижением в подтверждённые знания.

Такой подход позволяет расширять базу знаний по стендам, версиям и функциям продукта без жёсткого кодирования поведения конкретных сущностей в Core.

## Безопасность

- Секреты не печатаются в отчётах и не передаются LLM.
- Saved credentials использует только доверенный runtime.
- Неизвестное действие блокируется.
- Любая мутация проходит через action-policy.
- Cleanup ограничен точной ledger-записью.
- Успешный HTTP-вызов сам по себе не равен успешному cleanup: требуется post-check.
- Cleanup через прямое изменение базы данных или произвольные SSH-команды запрещён.
- Все значимые cleanup-события сохраняются для аудита.

## Проверка качества

Перед установкой изменений выполняются:

- резервное копирование изменяемых production-файлов;
- синтаксическая проверка Python-модулей;
- изолированные smoke-tests planner, policy, browser semantics, ledger, cleanup и blockers;
- безопасные runtime-прогоны без реального destructive-действия, если точная цель или поддержка операции не подтверждены.

Постоянный smoke-suite должен запускаться одной командой из стабильного каталога и не зависеть от временных файлов.

## Текущее состояние

Реализовано:

- v069 action-policy;
- исправление read-only detector для managed workflows;
- сохранение последовательного workflow одним test case;
- persistent resource ledger;
- Cleanup Manager с навигационным replay и проверкой точного ресурса;
- семантическая работа с точной строкой и context menu;
- metadata-driven REST cleanup;
- изоляция destructive REST tools внутри Cleanup Manager;
- product blocker registry;
- команды просмотра статуса и blockers.

В работе:

- сокращение model-facing контекста и времени одного tool-call без изменения
  архитектуры STEP/AUTO и action-policy;

Текущая история операционной проверки:

- Для зелёного lifecycle выбрана Location: документация подтверждает создание через collection endpoint и архивирование точного объекта через `POST <collection>/<uid>/archive`.
- Три запуска regression planner завершились до первого browser-действия из-за зависшего процесса Ollama `qwen3:14b`, включая контрольный запуск с уменьшенным context window. После перезапуска Ollama минимальный запрос и planner снова заработали.
- Эти попытки корректно сохранены как `BLOCKED`; ни одного test resource не создано и destructive-действия на стенде не выполнялись.
- Повторный lifecycle подтвердил корректный план из одного case, но browser state разросся примерно до 74 тысяч символов и model-call превысил timeout до первого WRITE. Первый уровень ограничения снизил критическую точку примерно до 51 тысячи символов, но последовательные states снова начали накапливаться. Поэтому добавлено сворачивание старых browser results в короткую историю; lifecycle нужно повторить после установки обоих уровней.
- Следующий прогон подтвердил стабильный контекст 26–38 тысяч символов, но обнаружил неверную ветку `Administration → General settings` для Location. WRITE был отклонён до создания объекта. Resolver дополнен семантической категорией справочных сущностей, а preflight теперь требует соответствия текущей страницы целевому ресурсу.
- Контрольный прогон затем успешно создал Location, сохранил её точное имя и ID в resource ledger и выполнил реальный `POST <collection>/<id>/archive`. Поскольку архивная запись остаётся в collection, verifier был уточнён: archive проверяет архивный признак, DELETE — отсутствие. Повторный cleanup распознал уже архивный объект и закрыл ledger без второй мутации.
- Итог Job остаётся `BLOCKED`, а ресурс имеет статус `cleaned`: это корректное разделение verdict сценария и lifecycle ресурса. Причина BLOCKED — модель повторно выдумала `role=option` при проверке строки таблицы, хотя runtime такой роли не наблюдал.
- Следующий реальный Job подтвердил новый table-row inspector: Location создан, точная строка найдена с одним совпадением, ledger зарегистрирован, а Cleanup Manager успешно архивировал ресурс. Case остался `BLOCKED`, потому что модель попыталась выполнить Archive сама и повторила действие после policy denial; после прогона добавлены provenance-проверка `external_id` и guard повторной запрещённой мутации.
- Контрольный Job после этих guards прошёл весь lifecycle без прямой архивации: create, machine-locked table evidence, ledger с пустым неподтверждённым external ID и Cleanup Manager archive успешны. Итог остался `BLOCKED` только потому, что модель сохранила точные planned titles под собственными IDs `check-*`; добавлено детерминированное восстановление `planned-*` по уникальному точному title.
- Первый свежий Job после восстановления planned IDs завершил case с `PASS=1`: Location создан, точная строка подтверждена, ресурс зарегистрирован без выдуманного external ID. Первичная cleanup-попытка осталась `cleanup_failed`, потому что Core ещё не различал intent-click и отдельную кнопку подтверждения Archive.
- Визуальная проверка этого Job уточнила причину: первый пункт `Archive` лишь открыл отдельный confirm-popover, а строка осталась активной. Core больше не считает такой intent-click выполненной мутацией и требует отдельный policy-controlled клик по одноимённой кнопке подтверждения.
- После исправления тот же Job безопасно восстановлен: оба destructive-клика прошли отдельные v069 confirmations, фактический Archive выполнен, а новый recovery без повторной mutation подтвердил `Unarchive` в context menu той же exact-строки. Итог: Job `passed`, case `passed`, три planned checks `passed`, resource `cleaned`, cleanup `completed`.

## Правило актуализации документа

Документ обновляется при каждом изменении архитектуры, набора возможностей, policy, persistent state, cleanup-механизма, knowledge pipeline или известных ограничений. Временные эксперименты сюда не добавляются, пока они не стали частью установленной и проверенной системы.

Исходный код и архитектурные документы версионируются через Git. Runtime state, credentials, browser artifacts, рабочие базы данных и временные резервные копии не входят в репозиторий.
