# Справочный ответ, предложение и исполнение

## Статус и обнаруженное ограничение

Проект следующего контракта, не реализованный режим и не заявленная новая способность. Native диагностика v210 показала две разные проблемы: правильный источник найден, но пересказ неточен; затем Core потребовал тестовый JSON от задачи-объяснения. Извлечение, применение источника и завершение задачи должны проверяться отдельно. Уменьшение нерелевантного контекста само по себе не делает ответ достоверным.

## Три результата

| Намерение пользователя | Допустимый результат | Что он не означает |
|---|---|---|
| Объяснить известную логику, предложить автоматизацию | Справочный ответ с источниками, ограничениями и неизвестными | Выполнение, готовность конфигурации или PASS |
| Проверить поведение | Проверки по locked expected и пригодным текущим evidence | Свободный пересказ вместо oracle |
| Создать или применить решение | Отдельное разрешённое исполнение через policy, scope и журнал | Разрешение из текста предложения |

Намерение не выбирает сама модель. Доверенный входной слой должен сохранять явный тип задачи. Для неоднозначного смешанного запроса безопасен отказ от исполнения до уточнения, а не превращение любого слова «как» в исключение из проверки. Уже запущенный тест с planned checks нельзя задним числом объявить справочным, чтобы обойти BLOCKED.

## Границы будущей реализации

1. Справочный Job получает отдельный immutable contract до первого model turn. Не допускаются тестовые planned checks, mutation workflow/stage или присоединение операций к такому контракту. Неизвестный/противоречивый режим отклоняется; существующие Job сохраняют прежнее поведение.
2. Каталог справочных инструментов ограничен точным allowlist чтения знаний и зарегистрированных схем. Класса OBSERVE самого по себе недостаточно для разрешения любого SSH/API чтения. Проверка allowlist выполняется также при dispatch: скрытие инструмента от модели не является защитой. Даже общее лабораторное разрешение не превращает предложение в запрос выполнить его.
3. Для текущего обследования UI нужен отдельно явно разрешённый read-only contract. Исторический источник не становится текущим runtime evidence. Предлагаемый endpoint/payload проверяется по установленной схеме, а не по догадке; неизвестные enum/версии остаются неизвестными.
4. Справочный результат хранится отдельно от тестового verdict, с business_verdict отсутствующим и evidence_for_pass=false. Даже если модель прислала UQA_CHECKS_JSON, он не записывается как пройденный тест и не меняет статус существующего case. Конкретный формат хранения требует отдельной реализации и миграционного теста, не придумывается по факту ответа.
5. Ссылки сверяются с фактически извлечёнными approved sources и разрешённой историей. Выдуманный observation ID, чужой case или неподтверждённая версия не принимаются за основание. Корректная ссылка не гарантирует корректный пересказ: противоречия и неизвестная применимость показываются явно, автоматического verified promotion нет.
6. Исполнение предложенной процедуры требует нового явного запроса и отдельного execution Job с актуальными scope, policy, locked oracle и журналом. Справочный Job не повышается до исполнительного. Предыдущий свободный текст модели не является binding.

## Минимальная приёмка

Проверить: обычное объяснение без test JSON; обычный тест по-прежнему требует supported checks; попытку сменить режим после начала; смешанную задачу; модельный вызов скрытого WRITE/DESTRUCTIVE/неизвестного инструмента; OBSERVE вне allowlist; выдуманные citations/observations; исторический source вместо текущего proof; предложение выполнить без пользовательского согласия; повторное использование чужого scope; отсутствие записи PASS и product-memory promotion из справочного текста. Затем нужен новый native прогон локальной модели без операторских chunks. Содержательная точность ответа измеряется отдельно от правильности маршрутизации.
