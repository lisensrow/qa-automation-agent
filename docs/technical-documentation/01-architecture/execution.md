# Поток исполнения задачи

v530: чтение собственного исторического результата различает успешное выполнение задачи и наличие хотя бы одного сообщённого пользовательского экземпляра Tray. Пустые массивы не доказывают значок/меню и не дают полного PASS. Контекст дополнительно передаёт фактический отрицательный запрет повтора из уже действующей защиты; он не создаёт разрешения. На обеих ОС модель после этой операторской доработки верно разобрала6/6проверочных фактов; первоначальные5/6ошибки сохранены. Это ограниченная проверка интерпретации с подготовленными фазами, не полная автономная приёмка регресса.

v523: ограниченный Tray-start профиль компилирует только action=start из проверенного источника поставки; общие Core WRITE, журнал и защита от повторов сохраняются. Модель выбирает готовность, отправку и чтение своей задачи. Проверка собственной задачи и явной вложенной ошибки не доказывает значок, tooltip, меню, пользовательскую сессию или полный кейс. Отсутствующий полный источник шагов блокирует кейс, а не разрешает генерировать действия из его названия. Подготовка источника/ожиданий/фаз оператором отражается отдельно от исполнения моделью.

## Аудиты и автономность

В штатном typed audit runtime модель сама выбирает retrieval, текущую readiness, разрешённый pluginAudit при stale inventory, новый osAudit, чтение собственного результата и canonical report. Это prepared профиль: scope/oracle/catalog задаются заранее, не обещается общий свободный NL вход. Исторический expected связан с первичным Job, а не со свободным текстом LLM. Отчёт строится независимо и не принимает придуманные evidence IDs/статусы. Execution journal закрывается только по native receipt и свежему own-task result; для refresh дополнительно требуется точный loaded plugin inventory. Такое подтверждение исполнения не равно бизнес-PASS. Старые операции без заранее объявленного verification contract остаются в прежнем состоянии. Операторская подготовка, делегированные подтверждения policy и runtime-вмешательства учитываются раздельно; успешные прототипы не подменяют приёмку штатного runtime.

Pinned delivery допускает пока только osAudit1.3.4 на core1.3.27, без удаления и с проверкой ОС; отдельный WRITE audit tool допускает только pluginAudit/osAudit без произвольных параметров. Операторский pipeline обеих ОС дошёл до fresh result. Скачивание не загрузка: pluginAudit обновил stale snapshot и подтвердил loaded/no load error без перезапуска. Полный case не PASS: legacy OS name/version baseline изменился. Подготовка/выполнение оператором не засчитываются как модельная автономность. Следующая приёмка должна проверить именно model-selected retrieval → preflight → task → fresh fetch → locked oracle → report, отдельно учитывая каждый тип вмешательства.

## Pinned core update

Узкий updateAgent инструмент v299 принимает только точную КЕ, agent_id и числовую версию из locked case/исходного запроса. До POST выполняет текущие GET identity/online/version и полного списка прежних updateAgent tasks. Обычные WRITE confirmation и журнал остаются обязательными. Запрещены latest/downgrade/повтор; сомнительный ответ не повторяется. Два операторских пилота подтвердили core1.3.27/online на Windows и Astra, но не автономность модели или регресс. Version reconciliation ещё не поддержан: журнал сохраняет awaiting_verification, отдельный postread не снимает блокировку отправки. Конкретные доказательства и границы приведены в основном плане UQA_AGENT_PLUGIN_REGRESSION_PLAN.md.

## Узкий ordinary condition entry

Whole-request adapter v284 может до LLM planner построить один immutable case для явно названного CMDB/new unsaved/AND/неархивных Endpoint с Ubuntu или Windows/no Save. Expected выводится только из целого исходного запроса; hash и повторный разбор проверяются в runtime. Неподдержанный текст не обрезается и остаётся старому planner. STEP/AUTO и confirm_mutations не меняются. Это конкретный поддержанный вход, не общее создание коллекций; границы и native evidence приведены в [контракте условий](condition-draft-contract.md).

## Составное добавление условия

Контракт следующего runtime и реализованные границы компилятора: [условия коллекций](condition-draft-contract.md). Профиль и expected принадлежат caller; модель выдаёт только логические условия, не UI-аргументы.

Архитектурный эксперимент245 проверил разделение ответственности: модель извлекает только logical plan; независимая проверка сравнивает его с заранее объявленным expected; trusted compiler выбирает UI primitives и аргументы; действия проходят обычную policy. Три строки/четыре значения подтверждены receipt во время соответствующих действий. Это ещё не production entry, не проверка итогового DOM после всех строк и не сохранение. Перед переносом нужны явный supported profile, неизменность источника/ожиданий и независимый fresh readback, а не доверие свободному prose/готовой картинке.

Универсальный WRITE-композит добавляет одну новую строку из наблюдённого draggable treeitem и заполняет exact row/column controls. Он ограничивает размеры входа, требует наблюдённые session/URL, проверяет их между стадиями, не редактирует существующую строку и не вызывает submit. Сбой после начала остаётся partial/uncertain; автоматический повтор и откат запрещены. Обычная policy и compatibility checks применяются перед вызовом. Это объединение UI primitives, не доказательство сохранённого AST или выполнения бизнес-логики. Отдельный pinned reviewed recipe может загрузить его schema в model catalog, но не выполнить вызов и не выдать разрешение.

## Восстановление расположения поля

После реального отказа fill/select Core может один раз перейти к вкладке, указанной перепроверенным источником исходного задания. Нужны running Job/case с write profile, прежняя confirm_mutations policy, единственный текущий tab и отдельная свежая инспекция роли, видимости, enabled и selected=false в той же session/URL. Обычная ссылка или произвольный текст не подходят. Разрешён только INTERACT переход, не fill/save. Evidence помечается Core navigation recovery, а не выбором модели. Дальнейшие инструменты проходят обычные проверки. Повтор того же recovery запрещён; STEP/AUTO, v069, oracle и журнал не меняются.

v234: документированный родительский раздел может объяснять уже наблюдённый вход. Source-rechecked product adapter возвращает label без URL/команды/разрешения. Core сверяет его с leaf фактического успешного browser_open_page и единственным navigation label той же native entry с session; новый редактор дополнительно требует прежней same-session/origin approved transition. Неизвестный источник, отсутствие/дубли label и неподдержанный формат не обходятся. Это проверка навигационного предусловия, не право создания: v069, stand lock, journal и oracle продолжают действовать. Product-specific соответствие берётся из отдельно принятой декларации руководства, не из свободного model prose.

Справочный `/advice STAND QUESTION` — отдельный явный вход, не новая ветка STEP/AUTO. Он создаёт knowledge-only Job, использует фиксированный read allowlist и не входит в обычный test run_turn. Ответ находится в advisory.state/response, не становится PASS/FAIL и не запускает предложение. MVP не обследует текущий UI/API и не выбирает режим автоматически по словам пользователя. Подробнее: [advisory contract](advisory-contract.md).

1. Пользователь задаёт стенд, область действий и expected. Если критерия нет, агент ищет документацию/уточняет, не сочиняет успешный результат.
2. Core создаёт persistent Job, cases и planned checks либо материализует поддержанный prepared/locked сценарий.
3. Runtime наблюдает UI/API и при необходимости читает документацию/совместимую память.
4. Модель выбирает доступный инструмент. Core проверяет stand lock, action classification, policy и контракты workflow.
5. Перед известным commit durable journal фиксирует intent и неизменные tool/arguments/oracle. Повтор неопределённой операции не отправляется вслепую.
6. Native adapter выполняет действие или возвращает доказанный отказ до отправки. Результаты связываются с session, case, observations и evidence.
7. Поддержанный evaluator сравнивает expected с фактическими данными. Модельный текст не заменяет обязательное доказательство.
8. Сохраняются итог, ресурсы, блокеры и cleanup state. Knowledge accumulation выполняется только в пределах существующего узкого pipeline; универсальный exporter всех исходов ещё отсутствует.

## STEP и AUTO

Режимы архитектурно сохранены. AUTO не означает снятие WRITE/DESTRUCTIVE подтверждений. Подготовленный Job позволяет повторяемое исполнение одного сценария, но повторные мутации всё равно ограничены durable journal и permission scope.

## Важные ограничения

Нет полного natural-language compiler произвольных lifecycle-контрактов. Физический outbound/UI guard для всех unknown autosave не закрыт. Существуют legacy paths без полного owned protocol. Длительность/нестабильность продукта и контекста модели не снимают ограничения безопасности.

Новая память v1 сейчас вызывается доверенным операторским кодом. Она не подключает новые model tools и не меняет этот execution flow.
