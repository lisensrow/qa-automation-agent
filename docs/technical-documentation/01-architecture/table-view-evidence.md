# Таблицы: контекст, строки и поля

## Статус

Проект контракта следующего этапа, не реализованный новый verdict validator. Текущий observer таблицы и безопасная горизонтальная прокрутка реализованы; общий typed table-count/cell proof пока отсутствует. Существующий контракт поиска и его допустимый unique-visible fallback не меняются.

## Зачем отдельный контракт

Имя, переданное в inspector, не является наблюдённым именем таблицы. Единственная неназванная таблица общей CMDB не доказывает просмотр выбранной коллекции. DOM snapshot_complete означает отсутствие превышения бюджетов наблюдателя, не полноту виртуализированных строк, колонок или всего набора данных. Наличие поля в API не доказывает его отображление; текст имени машины не заменяет ячейку ОС. Поэтому добавление visible_row_count в generic ui_assertion без контекста было бы недостаточным.

## Вход из неизменного ожидания

До выполнения зафиксировать требуемый view, идентичность объекта, поле, тип сравнения и область количества. Различать количество отрисованных строк, число загруженных строк API, полный состав и серверный total. Не выбирать трактовку после получения удобного ответа. Понятный человеку запрос превращается в структурное ожидание; неподдерживаемое ожидание даёт BLOCKED, не молчаливую замену проверки.

## Цепочка доказательств

1. Исполненная native-навигация в нужный view текущей browser session, фактический origin/route, привязка к точному объекту. Запрошенная ссылка или receipt без фактического перехода недостаточны.
2. Свежая полная конфигурация выбранного объекта и отдельно ответ данных того же ID, источник и request ID. Никаких выдуманных запросов или исторических ID без повторной сверки. Для endpoint, где чтение использует POST, нужен отдельный reviewed read-source adapter; нельзя выдавать его за GET или расширять обычные POST-разрешения.
3. Native DOM-наблюдение этой таблицы после перехода и загрузки. Session, Job/case, порядок evidence и view должны совпадать; navigation/reset инвалидируют прежнюю привязку. Unique-visible resolution можно использовать только вместе с независимо доказанным view, не как доказательство запрошенного имени.
4. Для UI cell — точный заголовок, однозначная строка и наблюдённая ячейка. Для данных API — точный путь поля и независимая идентичность строки; такой результат не подменяет UI cell. Прокрутка возвращает новые снимки, но сама не доказывает наличие всех колонок.
5. Для полного состава — проверенная пагинация, offset/limit/count/total, уникальные ID и отсутствие пропусков. Серверный total не равен числу видимых строк. Несогласованность источников или отсутствующая колонка сохраняются как расхождение/BLOCKED в зависимости от исходного oracle, не исправляются модельным текстом.

## Границы доверия

Verifier получает сохранённые native evidence и linked observations, а не утверждения модели о том, что таблица принадлежит объекту. Source/profile validation и locked oracle независимы от memory retrieval. Исторический рецепт помогает выбрать действие, но не является доказательством текущего результата. Кастомные operator census остаются диагностикой без права PASS; candidate знания не повышаются автоматически.

## Минимальная приёмка реализации

Положительный сценарий — правильный view, одна текущая строка, точная видимая ячейка и согласованный первичный источник. Отрицательные сценарии: корневая CMDB вместо коллекции; имя вместо ID; другой объект/stand/session/case; stale evidence; перестановка evidence; смена view после чтения; duplicate headers/IDs; неполная пагинация; виртуализированная отсутствующая ячейка; поле есть только в API; None вместо числа; bool вместо integer; ошибочный named fallback. Каждый отказ проверять независимо, старые BLOCKED не переписывать. После fixture-приёмки нужен новый реальный локальный model-run без операторской навигации и с тем же заранее зафиксированным ожиданием.
