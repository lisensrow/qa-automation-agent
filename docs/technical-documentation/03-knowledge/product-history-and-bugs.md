# История продукта, ОС, изменения поведения и баги

Цель памяти — сохранять проверяемую историю каждой функции: как работала на конкретной ОС/версии, что изменилось, какой баг подтверждён и где объявлено исправление. Не имитировать «всезнание»: ненаблюдённая история остаётся неизвестной, гипотеза не становится воспоминанием.

## Идентичность истории

Устойчивый concept ID связывает функцию между релизами. В scope могут быть os, os_version, agent_architecture, agent_version, plugin_version, server_version, frontend_version, feature_profile и document_revision. Только существенные параметры; неизвестные явно unknown, без автоматического переноса на соседний patch или другую ОС.

Canonical claim хранится один раз; typed value создаёт variant, область версии/ОС — отдельный scope. Разные values в разных release scopes означают разные варианты истории, не автоматически конфликт. Разные values одного утверждения в одинаковом scope/source level — conflict для проверки. Старые manifests/подтверждения не удаляются.

read_history даёт ограниченное read-only представление по project/namespace/concept, с scope/status/source level и датами первого/последнего подтверждения. Эти даты отражают поступление подтверждений, а не автоматически дату релиза. has_more сообщает об обрезанной выдаче; это не «полная история продукта». Текущий API доверенный операторский, не подключён к LLM loop и не интегрирует автоматически старые facts.

## Баг — не любое несовпадение

Runtime может сохранить observed limitation/suspected regression, но сам не назначает confirmed bug. Для структурированных predicates issue_classification и declared_fix_version обязателен source_level=developer_confirmation, knowledge_kind=limitation, issue_id и источник, одобренный trusted registry как developer_confirmation с approval_role=developer.

Issue decisions ограничены confirmed_bug/not_a_bug/needs_information. Заявленная fix version должна быть конкретной, не latest/unknown. Документ общего назначения, мнение модели или только неуспешный тест не заменяют developer attribution. В этом этапе атрибуция developer source подтверждается оператором registry; автоматический Jira/signature/пользовательский RBAC verifier ещё не реализован. Все такие записи всё равно candidate, не автоматическое semantic acceptance.

Предлагаемая цепочка: наблюдённое отклонение → решение разработчика → объявленная fix version → независимая проверка фикса на нужной ОС/версии. Исправляющий commit сам по себе не доказывает устранение симптома. fix_verification требует runtime source и issue ID, но candidate admission не доказывает произвольный claim о прохождении проверки.

## Как будущий агент будет отвечать пользователю

Безопасная формулировка различает: «такой симптом наблюдался», «разработчик признал баг», «исправление заявлено в релизе» и «исправление подтверждено повторной проверкой». Совет обновиться должен учитывать точное соответствие симптома, условия/ОС, источники разработчика, known affected/fix versions и состояние верификации/совместимости.

Рекомендующий rule engine, сравнение нового live результата с историей, promotion подтверждённого фикса и рекомендации обновления — следующие этапы. read_history возвращает upgrade_advice_authorized=false. Сейчас UQA не объявляет автоматически баг исправленным и не обновляет агента на основании памяти.
