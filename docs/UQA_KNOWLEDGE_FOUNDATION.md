# Общая база знаний UQA: фундамент и масштабирование

## Назначение, принятое пользователем

Обновлено 14 октября 2026. Главная идея проекта — масштабируемая автоматизация на основе общей проверяемой памяти, а не набор разовых скриптов. QA-агент — первый потребитель. В дальнейшем те же знания должны использовать агенты документации, разработки и технической поддержки, с собственными правами и правилами использования.

Масштабирование общей базы знаний — постоянный приоритет архитектуры: стандартизация опыта, повторное использование разными агентами, версии, источники и доказательства. Общая память должна обслуживать не одну LLM, а совместимые роли QA, документации, разработки и техподдержки.

Ожидаемый результат — воспроизводимые проверки, фактический и ожидаемый результат, доказательства и понятная неопределённость. Абсолютное отсутствие ошибок не гарантируется. Исторический успех не заменяет новую проверку, а наличие памяти не обучает веса LLM.

## Уже существует

- Документный индекс SQLite FTS5: knowledge/source → knowledge/index/knowledge.db → knowledge_search. Markdown-рецепты могут читаться локальной LLM вместе с руководствами. Это лексический поиск с ограниченными результатами, не embeddings и не гарантия полноты.
- Отдельный product knowledge store хранит scoped candidate/verified facts и confirmations. Retrieval ограничивает версии и типы фактов; сейчас поддержаны ui_api_binding и ui_navigation. Произвольный рецепт не следует проталкивать в эти типы или искусственно помечать verified.
- Runtime Jobs, observations, evidence, resource ledger и operation journal сохраняют первичную историю. Они не являются публичным корпусом и не экспортируются целиком.
- v174 добавляет index_document: транзакционная замена чанков только одного подготовленного документа. Остальные источники и их row IDs сохраняются. Пустой документ, неподдержанный формат, внешний путь или выход через symlink не удаляют прежние знания. До записи делается согласованная резервная копия индекса. Автоматический сбор любого произвольного теста этим не реализован.

## Формат опыта и стандартизация

Каждая новая запись опыта должна иметь стабильный record ID, schema version, knowledge kind, область продукта/функции, язык, дату наблюдения/пересмотра, источники и ограничения. Для следующего typed ingestion-контракта предусматриваются:

- knowledge_kind: recipe, observed_fact, limitation, test_experience или project_decision;
- execution_mode: live_operator_assisted, live_autonomous, isolated_fixture либо planned;
- validation_status: observed, runtime_verified, candidate, contradicted, deprecated; признание успеха не смешивается с режимом выполнения;
- scope: установка/архитектура, backend/frontend/agent/plugin versions, ОС, feature/profile; неизвестная версия явно unknown, а не latest;
- provenance: Job/case/evidence/observation references, источник документа и hash, проверявший исполнитель и границы проверки;
- expected/actual/verdict, preconditions, безопасный рецепт, известные ошибки, условия повторной проверки;
- sensitivity/access_scope, supersedes/conflicts_with, compatibility и review due. Отдельные доверенные метаданные, недоверенный текст источника и внешние инструкции.

Сейчас reviewed записи представлены Markdown-источниками с явными метаданными и разделами; эта полная машиночитаемая схема и её валидатор ещё не внедрены. Не выдавать документный FTS за version-gated verified facts. Рецепт надо перепроверять на текущем стенде даже при выдаче поиска.

v175 реализует первый ограниченный atomic candidate формат в product_knowledge_records.py: contract/observed_fact/limitation/test_experience, scoped variants, source manifests, event/source dedup и explicit conflict. Остальная полная схема, recipe/code validators и promotion остаются далее. read_history позволяет оператору просмотреть версии/ОС и источники, но ещё не подключён к автоматическому LLM recall. Существующие verified facts/retrieval не заменены.

Уточнение цели: сохранять историю функций по конкретным ОС, ядру, плагину и компонентам сервера/фронта, а не только последнюю инструкцию. Разные release scopes не перезаписывают друг друга. Баг/объявленная fix version требуют developer_confirmation и issue_id; наблюдённый симптом и предположение модели этого не заменяют. Заявленный фикс и его runtime верификация раздельны. Совет обновиться пока не включён и должен опираться на конкретные affected/fix versions, ОС, авторитетный источник и состояние проверки, а не похожую фразу из поиска.

Официальные руководства остаются отдельными источниками с hashes/revisions/applicability, проектные документы UQA не подменяют спецификацию UC. source integrity не доказывает semantic entailment. Автоматический watcher редакций и byte-snapshot importer ещё не внедрены; уже имеющиеся руководства сохраняются. Документационный пакет для обмена — technical-documentation/README.md.

Для происхождения данных ориентир — W3C PROV: сущность знания, действие проверки и ответственный исполнитель, связи источников и производных записей. Это проектное направление, не утверждение о реализованной PROV-совместимости. [W3C PROV overview](https://www.w3.org/TR/prov-overview/).

Для корреляции операций, retrieval и проверок ориентир — OpenTelemetry. Нужно фиксировать версию используемой convention и отличать стабильные общие схемы от развивающихся GenAI схем; интеграция OTel пока планируется. [OpenTelemetry specification status](https://opentelemetry.io/docs/specs/status/), [semantic conventions](https://opentelemetry.io/docs/specs/semconv/).

## Обязательный порядок пополнения

1. Сохранить первичные evidence и итог, включая FAIL/BLOCKED и неудачные гипотезы. Отсутствующий результат не дописывать по догадке.
2. Сформировать очищенное описание и минимальные provenance references; убрать credentials, заголовки авторизации, приватные данные и сырой stdout. Redaction одного writer не гарантирует безопасность любого нового источника.
3. Разделить актуальный рецепт, наблюдённый факт, технический fixture и известное ограничение. Учебный опыт пригоден для подсказки, не для объявления продуктового PASS.
4. Проверить scope/версии и валидность источников. При смене интерфейса/схемы или конфликте — recheck/candidate, а не автоматический перенос.
5. Добавить только reviewed источник и проверить его выдачу штатным knowledge_search. Не переиндексировать все старые файлы без необходимости.
6. Версионировать очищенный источник и код; DB, Jobs, секреты и artifacts оставить вне Git.

Это постоянное правило разработки. Автоматическая запись всех видов тестов, в том числе каждого fixture runner, требует отдельного проверенного ingestion-hook; нынешний ограниченный автоматический pipeline фактов этого не покрывает. Нельзя обещать, что уже перенесены все исторические тесты.

## Этапы масштабирования, ещё не реализованные

1. Расширение ограниченной v175 atomic schema до recipe/code types, semantic validators/promotion и специализированного OS/core/plugin source proof; развитие trust/secret gates и миграций.
2. Безопасный post-run exporter всех итогов, включая отрицательные, с outbox/retry без потери и без повторного выполнения бизнес-действий.
3. Разделение canonical records, неизменяемых доказательств и заменяемых поисковых индексов. Опыт можно переиндексировать без перезапуска тестов.
4. Hybrid retrieval только после измерения качества текущего FTS; оценка полноты, version filtering, конфликтов и false-pass на фиксированном наборе. Embeddings не вводить вместо контрактов.
5. Read API для разных агентов с изоляцией организаций/стендов, ролевыми правами, citations/provenance и совместимой схемой. Агент документации не получает WRITE на стенд вместе с доступом к памяти.
6. Перенос storage backend при измеренной потребности: миграции, нагрузочные проверки, concurrency, backup/restore; не вводить распределённую БД ради названия.
7. Evaluation/release gates: сценарий → oracle → execution trace → verdict → knowledge update. Принятые ограничения, coverage и время/стоимость видны в отчёте.

Расширение сверх памяти: общий реестр возможностей и проверяемых сценариев, capability discovery, version-aware adapters, независимый исполнитель проверок и replay sandbox. Это roadmap, не текущие возможности. Universal Core остаётся независимым от U-Connect-specific условий; STEP/AUTO и v069 policy сохраняются.
