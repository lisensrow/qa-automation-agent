## Самостоятельная проверка несохранённых условий

Явный requirement bounded_condition_draft фиксирует caller expected, source/profile/preparation hashes и один целостный критерий до генерации. Поддержанный профиль — плоский AND с уникальными Archived, CI class, OS name; операторы заданы отдельно для каждого поля. Нельзя переносить Wildcard на Archived/CI class или подменять неизвестную метрику OS name.

Runtime сам открывает настроенный стенд, проходит compatibility probe, Add → Add collection → Conditions через существующую policy. Модель получает найденное reviewed знание и возвращает только логический план. Чистый компилятор проверяет его независимо от модели; исполнитель добавляет свежие session/URL. Записанное до действий once-only состояние запрещает повтор частичной попытки или fallback к случайным кликам.

После всех трёх строк нужен новый readback всех шести ячеек: Operator и Value каждой строки. Ожидаемые значения: Archived/Equal/No; CI class/Equal/Endpoint; OS name/Wildcard/*Windows* либо *Ubuntu*. Успешные промежуточные receipts не заменяют итоговую проверку. OBSERVE передаёт hashes/длины без сырых значений страницы; обычный verifier сравнивает полный набор с caller expected, контекстом и порядком evidence. Последующий возможно выполненный WRITE делает старое чтение непригодным.

Статус не означает saved AST, корректность всей логической группы, пересчёт состава или создание коллекции. Свободное задание не маршрутизируется автоматически в этот явный prepared профиль. ## Политики и процедуры

Принцип caller expected → typed plan → прежняя policy → независимый readback переносим; конкретный collection profile не универсален. У политики должны быть explicit inactive, точный scope и отдельно подтверждённый эффект на выделенной КЕ. У процедуры — собственный граф, блоки/связи/параметры/переменные, saved graph и отдельный execution oracle. Схема create для обоих показывает default active=true: omission не означает безопасно отключённый объект. Историческое знание не разрешает создание или запуск.
