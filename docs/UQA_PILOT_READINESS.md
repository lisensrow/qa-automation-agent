# UQA: подготовка к обкатке ручных задач

Назначение: десять этапов подготовки, реальные доказательства и условия допуска. Это не заявление о готовности агента к любым задачам. Проверки на фикстурах не заменяют прогоны модели на стенде.

## Возможности, подтверждённые для пилота

- Read-only сценарий не получает инструкции создавать ресурсы.
- Исходные ограничения пользователя сохраняются при внутренних продолжениях Core.
- Повтор той же запрещённой мутации останавливает case как BLOCKED.
- Явный критерий одной видимой строки может фиксироваться до выполнения; Core проверяет фактическое количество совпадений.
- При полном доказательстве всех поддерживаемых read-only контрактов Core завершает case без лишнего вызова модели. Недостаток фактов не превращается в PASS.
- Статусы и evidence хранятся в Jobs, а знания используются как подсказка для нового прогона, не как доказательство.
- Требование compatibility probe выполняется как ограниченный OBSERVE через штатную policy; это не автоматическое разрешение WRITE.
- В реальном Monitoring сценарии три проверки навигации прошли, а отсутствие renderer errors не подтвердилось: Core сохранил FAIL, не общий PASS.

## Как обкатывать задачи отдела тестирования

Для каждого запроса сохранить: стенд, точное имя объекта, действие, ожидаемое поведение, ограничения на изменение данных. Затем сохранить план и итоговый Job. Проверить, что критерии не подменены и результат имеет пригодные evidence нужного case.

PASS — только проверенный критерий. FAIL — фактическое расхождение с фиксированным ожиданием. BLOCKED — нет доказательства, доступа, поддерживаемого контракта либо разрешения. Технический smoke PASS не означает PASS продуктового сценария.

Начать с точной строки и вкладок; затем чтение агентских фактов. Изменяющие задачи запускать только с policy, фиксированным тестовым именем и cleanup-планом. Для новых функций сначала наблюдать доступные UI/API, не угадывать endpoint и не внедрять product-specific ветвления в Core.

## Ограничения перед эксплуатацией

Финальная техническая проверка текущего патча: py_compile и smoke runner 193/193. Проверки с fixtures/mocks подтверждают защитные правила, не выполнение 193 пользовательских задач на стенде. Установлены ограничения safe compatibility probe и выделение положительного контекста навигации; реальная устойчивость форм всё ещё требует исправления. Не подменять BLOCKED успешным результатом и не расширять разрешение открыть Add до заполнения/сохранения.

Текущий Ubuntu telemetry Job сообщает ui/ci/agent online, но monitoring_age_seconds=48699.6 и monitoring_fresh=false (примерно 13,5 часа). Не использовать online как замену свежей телеметрии или readiness. Причина старой пробы не установлена; перезапуски и изменения расписаний не выполнялись. Проверить новую фактическую пробу перед запуском команды. Плагин-аудит доказывает чтение версии/времени аудита, не выполнение executeCommand.

Универсальное понимание любой ручной задачи пока не доказано. Узкая грамматика явно заданного критерия строки не является универсальным интерпретатором требований. Неподдерживаемые или неоднозначные критерии должны оставаться BLOCKED, а не упрощаться до удобной проверки. Повтор Monitoring подтвердил наличие известного renderer error signal, но не его техническую причину: соответствующий blocker не закрыт. Windows и Ubuntu не считаются online без свежего фактического наблюдения.

Следующая группа: устранить воспроизводимый form navigation/preflight BLOCKED; повторить открытие, чтение и закрытие без сохранения; затем уточнить реальные мастера. Новые owned resource lifecycle, выполнение команд и удаление ресурсов не входят в разрешение на открытие Add: для них нужны актуальные readiness-проверки и штатные подтверждения policy. Jira, full-back и универсальная новая-фича discovery остаются последующими направлениями.
